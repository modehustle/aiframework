# README.md — как водить систему

> Твоя личная настольная инструкция. Ты один управляешь разработкой на AI-агентах,
> и бываешь то планировщиком, то исполнителем. Этот файл — про то, как держать контур:
> что запускать в какой ситуации, на какой модели, что делаешь ты и что делает агент,
> и как не бояться git. Читай по делу, не подряд: открыл нужный раздел — сделал.

## 0. Установка

**Если репозиторий публичный:**

```sh
curl -fsSL https://raw.githubusercontent.com/modehustle/aiframework/main/installer/install.sh | sh
fraim init
```

**Если репозиторий приватный**, однострочник не сработает: `raw.githubusercontent.com` отдаёт
на приватный репозиторий 404 без токена. Клонируй тем доступом, который у тебя уже есть, —
установщик подхватит готовый клон и дальше будет обновлять его сам:

```sh
git clone git@github.com:modehustle/aiframework ~/.fraim/src   # или https://, как удобнее
sh ~/.fraim/src/installer/install.sh
fraim init
```

`fraim init` находит установленные харнесы — терминальные (Claude Code, Codex, Hermes, pi, omp,
OpenCode, Devin CLI, Gemini CLI, Qwen Code, Kimi Code, Mistral Vibe, Goose, Crush, Factory Droid,
Grok Build), IDE и редакторы (Cursor, GitHub Copilot, Cline, Kilo Code, Zed, Antigravity, Kiro,
Junie, Augment, Continue), Warp и OpenClaw; полный список и пути — в
[installer/README.md](installer/README.md#что-куда-ставится). Он раскладывает по ним 12 процедур
и мастер-скилл как Agent Skills (одной копией в общем `~/.agents/skills` для всех, кто его
читает), дописывает контекстный блок в их глобальные правила и заводит реестр проектов. Команда **идемпотентна**: она же
обновление, она же подключение только что поставленного харнеса. Устаревшие скиллы прошлых
версий она убирает сама, чужие — не трогает.

Поставить не `main`, а конкретную ветку (например, чтобы проверить неслитый PR):

```sh
FRAIM_BRANCH=имя-ветки sh ~/.fraim/src/installer/install.sh
fraim init            # разложить скиллы этой версии по харнесам
fraim version         # убедиться, что приехало то, что ждал
```

`fraim version` называет не только номер, но и **источник**: ветку, коммит и его дату.
Номер меняется, только когда о нём вспомнили, — а вопрос «приехало ли обновление» задают
между релизами, когда номер тот же:

```
0.10.0
  источник: /home/mark/.fraim/src
  ветка main · коммит 6354ee5 · 2026-09-05
```

Вернуться на `main` — та же команда с `FRAIM_BRANCH=main`. Переключение затирает всё, что
лежало в `~/.fraim/src` (это наша копия исходников, не твоя работа), и потому не может
упереться в git-конфликт. То же самое короче: `FRAIM_BRANCH=имя-ветки fraim update` —
одна команда вместо трёх, разложит по харнесам сама.

Для Claude Code есть и плагин — тогда обновления приезжают штатным каналом. Это путь для
**публичного** репозитория; на приватном ставь через `install.sh` выше:

```
/plugin marketplace add modehustle/aiframework
/plugin install fraim
```

Проверить, что получилось: `fraim doctor`.

### Обновления

```sh
fraim update            # привезти новую версию и разложить по харнесам
fraim update --check    # только узнать, не выходя из терминала: есть ли новее
```

`fraim update` делает обе половины сразу — привозит исходники и заново раскладывает
скиллы. Половинчатое обновление и было главной ловушкой: привёз исходники, забыл
`fraim init`, и `fraim version` показывает новое, пока агент читает с диска старые
процедуры. `fraim init` остаётся отдельной командой — она нужна и без сети, когда
поставил новый харнес и хочешь разложить по нему то, что уже есть.

**Само оно тебе скажет.** Проверка ходит на хост не чаще раза в сутки
(`update_check_days`) и только из тех команд, где сеть уместна: `fraim update`,
`fraim doctor`, `fraim init`. Ответ кладётся в кэш, и дальше про него знают все —
`fraim status` и меню читают **файл**, а не сеть:

```
payments-api
  · новая версия fraim на хосте (a3f19c2)         → fraim update
```

Находка помечена точкой, а не восклицанием: она про твою машину, а не про проект, и
вердикт по проекту не портит. Не хочешь её видеть — `fraim config set check_update off`;
не хочешь и самой проверки — `update_check off`.

**Настоящее автообновление** — то есть без тебя — делается одной строкой в том
планировщике, который у тебя и так есть (cron, launchd, systemd timer, Routines):

```sh
0 9 * * *  fraim update       # каждое утро привезти и разложить
0 9 * * *  fraim update --check   # или только сказать: exit 1, если отстали
```

Своего демона система не заводит — и не заведёт: это ровно тот случай, когда среда
принадлежит тебе ([C1](PRINCIPLES.md#c1-среда--это-выбор-пользователя-а-не-инвариант-системы)),
а сама она умеет **замечать**, а не действовать за тебя
([D4](PRINCIPLES.md#d4-планируем-обнаружение-а-не-действие)). Обновление посреди работы
подменило бы процедуры под уже запущенным агентом.

Вернувшись в проект, спроси сторожа — он детерминированный, без модели и без сети,
так что звать его можно сколько угодно:

```sh
fraim status
```

```
payments-api
  ! 23 коммита кода с последнего обновления ARCHITECTURE.md → /prune
  · 2 открытые задачи на доске                        → fraim tasks
```

### Когда работа идёт не в одном каталоге

Пока проект — это одна папка, сторож видит всё. Как только появляется второй чекаут —
ты завёл его руками через `git worktree` или это сделала за тебя среда вроде Orca, дающая
каждому агенту свой чекаут, — все остальные проверки продолжают смотреть в один каталог,
а работа идёт в другом. Сторож теперь это замечает:

```
payments-api
  ! задача «rate-limit» исполнена в чекауте «wt-rate-limit» и не запечатана → fraim task-seal rate-limit
  · 2 параллельных чекаута: wt-rate-limit, wt-add-auth                      → fraim fleet
```

Где именно живёт работа, показывает отдельная команда — read-only, как и сторож:

```sh
fraim fleet
```

```
payments-api
 ▸ /home/mark/projects/payments-api                  1 задача на доске
   /home/mark/orca/wt-rate-limit                     2 задачи на доске
✓ Orca (orca-ide) — рантайм отвечает
```

Список чекаутов ведёт **git**, а не среда: ответ верен и когда среда закрыта, и когда её
на машине нет вовсе — тогда `fraim fleet` просто не покажет последнюю строку.

Одна находка про среду появляется отдельно: если по этому проекту **по расписанию** ходит
агент со свободным промптом, ты об этом услышишь. Это не запрет — среда твоя
([C1](PRINCIPLES.md#c1-среда--это-выбор-пользователя-а-не-инвариант-системы)), — но правки,
приезжающие по будильнику, объясняют дрейф, который иначе выглядит беспричинным.
Запланированный `fraim status` находкой не считается: это наблюдение, а не правка.

Обе проверки выключаются как всякие другие: `fraim config set check_worktrees off`,
`fraim config set check_ade off`.

Рамка, из которой это выросло, — [MODES.md](MODES.md); разбор сред исполнения —
[installer/ADE_TARGETS.md](installer/ADE_TARGETS.md).

Если не помнишь команд — набери просто `fraim`, и откроется меню:

```
 ▌ FRAIM 0.10.0                                              payments-api
  ! 23 коммита кода с последнего обновления ARCHITECTURE.md   → /prune
  · нет удалённой копии — проект живёт только на этой машине  → fraim publish
  · 2 открытые задачи на доске                                → fraim tasks
  ───────────────────────────────────────────────────────────────────
  ▸ Скан проекта            что происходит здесь и сейчас
    Чистка                  прибрать всё, что чинится без суждения
    Копия вне машины        создать удалённую копию и отправить точки
    Обновить                поставить и обновить скиллы во всех харнесах
    Доктор                  что и куда установлено, что разошлось
    Реестр проектов         все проекты, которые ведёт система
    Добавить этот проект    зарегистрировать текущий каталог
    Настройки               что действует и откуда
    Выход

  ↑↓ выбор · Enter запустить · 1-9 сразу · q выход
```

Меню появляется **только в терминале**. Под пайпом — у агента, в cron, в CI — `fraim`
печатает список команд, как раньше: команда, ждущая нажатия, повесила бы сессию молча.

Завести проект под систему:

```sh
cd ~/projects/payments-api
fraim scaffold        # разворачивает фундамент и ai/, ничего не перезаписывая
```

Разгрести хвосты — одной командой (или пунктом «Чистка» в меню):

```sh
fraim clean           # покажет план и спросит; --yes чтобы без вопроса
```

Чистка делает только то, у чего ответ один и он вычислим: доводит фундамент до стандарта,
запечатывает расследования с записанным исходом, закрывает брошенные (старше 30 дней — в
архив с честной пометкой «исхода нет, уборка не проверялась»), запечатывает исполненные
задачи и сохраняет несохранённый фундамент. Папка расследования без `findings.md` — тоже
брошенное расследование: она закрывается по тому же правилу и получает отчёт, а не уезжает
в архив молча.

Гейты внутри неё остаются гейтами: задача без отчёта о фундаменте не уедет в архив. В конце
чистка перечисляет **поимённо**, что осталось и по какой причине, — числа в хвосте мало,
когда наверху экрана уже тридцать строк.

Чего она **не** трогает: доску задач, дрейф фундамента и отправку копии. Там нужно суждение,
и это работа человека и `/prune`.

Проекты, заведённые старой версией системы, доводятся до текущего стандарта одной командой —
сразу все проекты из реестра машины (и тот, в котором стоишь, если он под системой):

```sh
fraim upgrade         # все проекты реестра: доносит недостающее, ничего не перезаписывая
fraim upgrade ПУТЬ    # только один проект
```

Порядок после новой версии: `fraim update` (машина: исходники и скиллы) → `fraim upgrade`
(проекты). Проект с отсутствующим каталогом или не под системой пропускается с пометкой,
ошибка в одном не останавливает остальные.

Сторож сам скажет, когда это нужно: «фундамент отстал от стандарта: AGENTS.md CLAUDE.md
CONVENTIONS.md:Known-Pitfalls → fraim upgrade». Проверка идёт по **форме**, а не по номеру
версии: номер остаётся правильным, пока кто-то руками удаляет раздел.

Дальше `/bootstrap` (новый проект) или `/onboard` (код, написанный до системы) заполняют
развёрнутые файлы. Пока они не заполнены, сторож честно говорит «скелет развёрнут, но не
заполнен» — пустой фундамент никогда не изображает здоровье.

**Git знать не нужно.** Каждая точка сохранения здесь — коммит, поэтому репозиторий это часть
скелета: `fraim scaffold` заводит его, если его нет (внутри чужого — никогда). Дальше точки
ставят сами процедуры, а вернуться к любой можно, не зная ни одной команды git:

```sh
fraim undo            # показывает точки, поставленные системой
fraim undo a1b2c3d    # отменяет одну — встречным коммитом, историю не переписывая
```

Сторож заодно замечает то, чего git сам не скажет: что удалённой копии нет вовсе или что
точки сохранения с этой машины не уезжали. Это **не про бэкап** — это про досягаемость:
облачный агент, CI и вторая машина начинают с клонирования, и того, что осталось на диске,
для них не существует. Сам сторож копию по-прежнему не заводит — он называет команду,
которая это делает:

```sh
fraim publish         # спросит, где хранить, покажет план, проверит и отправит
fraim publish --check # только разведка: чем можно, что уедет, нет ли секретов
```

Как это устроено и что именно проверяется — [«Копия вне машины»](#копия-вне-машины-fraim-publish).

Ни одна процедура не попросит тебя выполнить git-команду. И ни один глагол не умеет «сохранить
всё»: сохраняются ровно те пути, которые он сам изменил, — поэтому `.env`, данные и твоя
незаконченная работа не уезжают в историю, и никому не приходится за этим следить.

Настройки — на двух уровнях, `fraim config` показывает не файл, а что действует и откуда:

```
  foundation_lag_commits 20     ← ai/fraim.conf
  foundation_lag_commits 20     ← ~/.fraim/config
  stale_plan_commits     1      ← по умолчанию
```

## 1. Зачем это всё и как оно устроено

Агенты сильны, но забывчивы: они дрейфуют, теряют контекст между чатами и любят
импровизировать. Система воркфлоу-команд лечит ровно это. Она оставляет в каждом
проекте **постоянный контекст** и ставит агенту **жёсткие рельсы**, чтобы ты в одиночку
вёл весь жизненный цикл и мог вернуться в проект через две недели, ничего не угадывая.

**Фундамент** — это всегда-актуальный контекст проекта, набор файлов в его корне:

- `ARCHITECTURE.md` — карта проекта (что это, компоненты, модель данных, интерфейсы).
- `CONVENTIONS.md` — правила дома: как тут работают + раздел `## Known Pitfalls / Lessons`
  (грабли, на которые уже наступали).
- `DECISIONS.md` — журнал решений, **только дописывается** (новое сверху, старое не стирается).
- `ai/` — рабочая папка: доска задач, архив, расследования.
- `STACK.md` — паспорт коробки (появляется, если проект развёрнут в Docker).
- `AGENTS.md` (+ `CLAUDE.md`-указатель) — правила проекта **для любого агента**, который его
  откроет. Фундамент едет в репозитории, и с этим файлом инструкция читать его едет вместе с
  ним: облачная сессия, CI, вторая машина или чужой харнес узнают правила из самого репозитория,
  а не из настроек твоего ноутбука.

> **Инвариант 0.4 — золотое правило.** `ARCHITECTURE.md` и `CONVENTIONS.md` читаются
> ПЕРВЫМ делом перед любой задачей и обновляются ПОСЛЕДНИМ шагом, без напоминания.
> `DECISIONS.md` — append-only. Устаревший фундамент считается багом, а не косметикой.

**Как идёт работа.** Почти всегда — **реактивная сессия**: ты пишешь агенту, он делает в
этой же сессии, любого размера, и сохраняется по ходу. Процедуры зовутся, когда работа
имеет особую форму: решить, что строим (`design-session`), заложить фундамент (`bootstrap`),
упаковать и выставить наружу (`deploy`, `/expose`), разобраться в непонятном (`/investigate`),
свести документы с реальностью (`/prune`, **садовник**), вернуться после паузы (`/orient`).

**Доска задач** — для работы **на потом**. Ты говоришь «запиши задачу» или «заведи проект» —
агент кладёт **карточку** в `ai/tasks/<slug>.md`: что сделать, зачем и как поймём, что готово.
Плана и контекста кода в карточке нет: тот, кто её возьмёт, прочитает фундамент и код свежими,
поэтому протухать в ней нечему. Проект — это **мастер-задача**, к которой привязаны подзадачи.
Говоришь «возьми задачу X» — агент делает её как обычную сессию и закрывает карточку строкой
итога. Ставит задачи на доску только человек: агент этого не предлагает.

**Петля для нового проекта (greenfield):**

```
design-session  →  bootstrap  →  (deploy)  →  [ реактивные сессии ]*
                                                 ↑ доска задач / orient / investigate / prune по ходу
```

**Он-рамп для уже существующего:** `/onboard` — едет в обратную сторону, одноразово,
после чего проект встаёт в обычную петлю.

Одна фраза «зачем» на каждый слой:

| Слой | Зачем |
|---|---|
| `design-session` | решить, ЧТО и ПОЧЕМУ строим — до того как появилась папка, код, контейнер |
| `bootstrap` | заложить фундамент кода, чтобы возвращаться с контекстом, а не угадывать |
| `deploy` | упаковать в безопасную Docker-коробку и написать её паспорт |
| `/make-task` | поставить задачу на доску: что, зачем, когда готово — по твоему слову |
| `/run-task` | взять задачу с доски и сделать её обычной сессией |
| реактивная сессия | сделать работу здесь и сейчас, без церемоний — режим по умолчанию |
| `/prune` | свести документы с реальностью, пока дрейф не сгнил |
| `/orient` | вернуться после паузы и понять, где всё стоит |
| `/expose` | впустить трафик к развёрнутому: прокси, сертификат, файрвол |
| `/onboard` | завести под систему то, что существовало до неё |

## 2. Дерево решений: «хочу X → что запускать»

Открыл таблицу, нашёл свою строку, запустил. Если в таблице нет твоей строки — это
нормально: значит это обычная реактивная сессия, работай без процедуры.

| Ситуация | Что запускать | Модель |
|---|---|---|
| Новый проект с нуля, ещё ничего нет | `design-session` → `bootstrap` → (`deploy`) | сильная |
| Готовый сервис без своего кода (n8n, Postgres, Redis) | `design-session` (короткий) → `deploy`. **НЕ** bootstrap | сильная / deploy — способная |
| Уже есть **мой код**, написанный ДО системы | `/onboard` (Секция 1). **НЕ** bootstrap | сильная |
| Уже есть **развёрнутая коробка** ДО системы | `/onboard` (Секция 2). **НЕ** deploy | сильная |
| И код, и коробка из прошлого | `/onboard` (обе секции) | сильная |
| Фича, правка, изменение — делаем сейчас | ничего не запускать — реактивная сессия | способная |
| Отложить работу на потом | «запиши задачу» → `/make-task` | любая |
| Большая работа из многих задач | «заведи проект» → `/make-task` (мастер-задача) | любая |
| Взяться за задачу с доски | «возьми задачу X» → `/run-task` | способная |
| Отдать работу дешёвой модели / раздать направления | «отдай воркеру», «раздай» → `/conductor` | способная |
| Вернулся после паузы, не помню статус | `/orient` | любая |
| Фундамент поплыл (сторож сказал про отставание) | `/prune` | сильная |
| Надо развернуть то, что собрал | `/docker-deploy` | способная |
| Развёрнутое надо сделать доступным снаружи | `/expose` | способная |
| Проект живёт только на этой машине, нужна копия на хосте | `fraim publish` — команда, не процедура | модель не нужна |

## 3. Шпаргалка по командам

По одной карточке на команду: **что · когда · модель · ты · агент · конец**.

### `design-session` — парадная дверь
- **Что:** думательная сессия. Решаем ЧТО строим и ПОЧЕМУ — до папки, кода и контейнера. Агент тут партнёр по размышлению, **не строитель**.
- **Когда:** самый старт нового дела.
- **Модель:** сильная.
- **Ты:** отвечаешь на вопросы, выбираешь из альтернатив, подтверждаешь финал.
- **Агент:** рамкирует задачу, раскладывает варианты, сводит к одному решению (с обоснованием и отвергнутыми альтернативами); ничего не создаёт, кроме одного артефакта.
- **Конец:** один артефакт — **Design Brief** (если это твой код) или **per-stack prompt** (если готовый сервис). С ним идёшь дальше.

### `bootstrap` — фундамент кода
- **Что:** кладёт фундамент авторского проекта: foundation-файлы + минимальный рабочий скелет кода.
- **Когда:** после `design-session`, для проекта со своим кодом.
- **Модель:** сильная.
- **Ты:** подтверждаешь дизайн (без «да» агент не пишет код), смотришь сгенерированные файлы.
- **Агент:** валидирует Design Brief; генерирует `README` / `ARCHITECTURE` / `CONVENTIONS` / `DECISIONS` + `.gitignore` + `.env.example` + `ai/`; затем скелет с entrypoint и health-эндпоинтом.
- **Конец:** фундамент стоит. Дальше `deploy` (когда есть что запускать) и петля make/run.

### `deploy` — коробка + паспорт
- **Что:** безопасно упаковывает стек в Docker и пишет паспорт `STACK.md`.
- **Когда:** когда есть что запускать (рано — для dev-коробки, поздно — когда есть функциональность).
- **Модель:** способная (механика + стоп-сигналы безопасности).
- **Ты:** вводишь хостовые пароли сам; подтверждаешь открытие портов; применяешь то, что пишется в `/etc` (nginx, certbot) — это хостовые действия, агент их не делает.
- **Агент:** выбирает режим доступа A/B/C, генерирует `compose` / `.env` / конфиги, проверяет, что наружу не торчит лишнее, пишет `STACK.md`; на хостовых шагах — стоп и просит тебя.
- **Конец:** запущенная защищённая коробка + `STACK.md`.

### `/make-task` — поставить задачу
- **Что:** кладёт на доску карточку `ai/tasks/<slug>.md` — что сделать, зачем, как поймём, что готово. Без плана и без контекста кода.
- **Когда:** ты сказал «запиши задачу», «на потом», «заведи проект». Только по твоему слову — агент сам этого не предлагает.
- **Модель:** любая.
- **Ты:** говоришь, что и зачем; для проекта — «заведи проект», для его части — «в проект X добавь…».
- **Агент:** уточняет недостающее одним вопросом, ставит карточку через `fraim task-new` (обычную, мастер-задачу или подзадачу проекта); глагол сам пишет служебную шапку и сохраняет.
- **Конец:** одна строка — что поставлено и куда. За работу не берётся.

### `/run-task` — взять задачу
- **Что:** берёт карточку с доски и делает её как **обычную рабочую сессию**: фундамент и код читаются свежими, решения принимает агент, развилки — к тебе.
- **Когда:** ты сказал «возьми задачу X» / «давай X из задач».
- **Модель:** способная.
- **Ты:** уточняешь по ходу, принимаешь итог.
- **Агент:** показывает доску, если задача не названа; у мастер-задачи предлагает взять подзадачу или разложить проект на подзадачи (список утверждаешь ты); старую карточку переспрашивает «ещё актуальна?»; делает работу с точками сохранения; сверяется с «Done when»; обновляет фундамент.
- **Конец:** итог по каждому пункту «Done when» и, с твоего согласия, `fraim task-seal` — карточка уезжает в `ai/archive/tasks/` со строкой итога. Проект закрываешь только ты.

### Как агент читает и пишет фундамент
- **Читает целиком:** `fraim brief` — карта, правила, действующие решения и доска одним выводом,
  строки перенесены, в конце метка «показано всё». Агенты любят читать первые 200 строк файла;
  здесь обрезать нечего.
- **Ищет записями:** `fraim find кэш cache` — ключи на обоих языках и основой слова, в ответ
  целая запись с заголовком, а не строка из середины абзаца.
- **Пишет глаголами:** `fraim arch "Раздел"` переписывает раздел карты, `fraim decide` кладёт
  решение наверх (заменённое само уезжает в архив), `fraim pitfall` — урок в свой раздел.
  Текст — агента, место и формат — системы.
- **Бэклог:** открытые вопросы, которые ты решил не терять, — `ai/backlog/`. В конце задачи агент
  перечисляет такие вопросы и спрашивает, какие записать; сам ничего туда не кладёт.

### Реактивная сессия — режим по умолчанию
- **Что:** обычная работа с агентом без всякой процедуры. Никакой команды запускать не надо.
- **Когда:** чаще всего. Вопрос, мелкая правка, разбор, изменение, форма которого проявилась по ходу.
- **Потолка нет.** Размер не важен: пока ты в сессии и решаешь сам — это законный режим,
  и превращать его в задачу не надо.
- **Что всё равно держится:**
  фундамент читается первым и правится последним (инвариант 0.4) ·
  поменялось поведение → строка в `DECISIONS.md` ·
  **наступил на грабли → строка в `## Known Pitfalls / Lessons`** (`CONVENTIONS.md`), с твоего
  «да»: это единственный способ, которым урок из сессии без процедуры доходит до следующей —
  каждая сессия читает этот раздел первым ·
  **точка сохранения на каждый законченный кусок**, а не в конце сессии — сессия может умереть.
- **Точка сохранения:** `fraim commit fix "<что изменилось>" <путь> <путь>`. Эти коммиты **и есть**
  запись реактивной работы, отдельного журнала нет.
- **Когда всё-таки задача:** не когда «стало большим», а когда ты сам решил отложить работу на
  потом или завести проект.

### `/prune` — садовник
- **Что:** сверяет фундамент с реальностью и **предлагает диффы** — сам не переписывает. Истина — код, не документы.
- **Когда:** когда сторож сказал, что фундамент отстал от кода, ИЛИ раз в 2–4 недели.
- **Модель:** сильная.
- **Ты:** одобряешь / правишь / пропускаешь каждый дифф; решаешь развилки (прав код или прав документ).
- **Агент:** Секция 1 (код → `ARCHITECTURE`/`CONVENTIONS`/`DECISIONS`), Секция 2 (`compose` + живое состояние → `STACK.md`); устаревшие записи `DECISIONS` **переносит** в `ai/archive/decisions_log.md` (не удаляет); противоречие код↔решение — **флагует как развилку**, сам не чинит; отмечает прунинг коммитом.
- **Конец:** что изменилось, сколько решений ушло в архив, и какие развилки оставлены тебе (возможные баги — починить сейчас или поставить задачей).

### `/orient` — вернуться с контекстом
- **Что:** строго **читает** — грузит фундамент и говорит, где всё стоит и что делать дальше. Ничего не меняет.
- **Когда:** вернулся в проект после паузы / в свежем чате.
- **Модель:** любая (лёгкая, read-only).
- **Ты:** читаешь сводку, выбираешь следующий шаг.
- **Агент:** первым делом спрашивает сторожа (`fraim status --json`), затем читает `ARCHITECTURE`/`CONVENTIONS`/`DECISIONS`/`STACK`/`README` + доску задач; даёт сжатую сводку (что за проект · доска · недавняя история · здоровье фундамента) и называет **один** следующий шаг.
- **Конец:** рекомендация команды. Сам работу не начинает.

### `/onboard` — он-рамп для существующего
- **Что:** заводит под систему то, что было ДО неё. Обратный bootstrap/deploy: **реальность → выведенные из неё документы → ратификация тобой**. Одноразово. **Неразрушающе** (код не двигается).
- **Когда:** открыл старый проект или коробку, у которых нет фундамента/паспорта.
- **Модель:** сильная.
- **Ты:** разрешаешь неоднозначности (что живое, что мёртвое), ратифицируешь черновики, **глазами проверяешь git-базу** (см. главу про git — самый опасный момент именно здесь).
- **Агент:** Секция 1 — **обнаруживает реальную структуру** (НЕ предполагает `src/`), выводит фундамент по факту, не двигая код; Секция 2 — документирует живую коробку, **не передеплоивая**, нарушения блюпринта заносит в «Deviations / legacy risks»; аккуратно ставит git-базу.
- **Конец:** фундамент + `ai/` + (паспорт) + git-база. Проект стал «обычным гражданином» → дальше `/orient` и обычная работа.

## 4. Выбор модели

Логика простая: **рассуждение — на сильной, обычная работа — на способной, дешёвая — только там,
где ей дали точный бриф.**

| Команда | Модель | Почему |
|---|---|---|
| `design-session`, `bootstrap`, `/investigate`, `/prune`, `/onboard` | **сильная** | проектирование и вывод архитектуры из кода — нужно рассуждение |
| реактивная сессия, `/run-task` | **способная** | агент сам собирает контекст и принимает решения |
| `/make-task`, `/orient` | **любая** | сформулировать намерение / прочитать и сводку дать |
| воркер флота (`/conductor`) | **дешёвая** | бриф пишет дирижёр прямо перед раздачей, по свежему дереву |

**Почему дешёвая модель — только во флоте.** Раньше задача была планом «под пол», чтобы её мог
исполнить слабый исполнитель. Но план — это снимок кода, и он протухал, пока лежал в очереди;
половина системы чинила это протухание. Теперь задача — намерение, а точный бриф для дешёвой
модели пишется **в момент передачи** и живёт минуты: дирижёр читает дерево, раздаёт и принимает.

## 5. Паттерны и антипаттерны эксплуатации

**Что укрепляет контур:**

- **Доска — только для отложенного.** То, что делаешь сейчас, делается сейчас, без задачи.
  Задачи на доске — это работа на потом или проект; если карточка висит месяцами, она, скорее
  всего, уже не нужна — закрой её с пометкой «отменена».
- **Фундамент — первым делом и последним шагом, каждую задачу.** Это и есть «всегда-актуальный контекст».
- **Сохраняйся по ходу.** Точка сохранения на каждый законченный кусок реактивной работы. Эти коммиты — и запись работы, и то, по чему система считает отставание фундамента.

**Что ломает контур (узнай в лицо):**

- **Копить несохранённое.** Работать час без единой точки сохранения, потому что «ещё не закончил». Сессия умирает вместе со всем, что в ней было.
- **Дать агенту «причесать» чужой код при онбординге.** Онбординг **документирует** реальность, он **не двигает, не переименовывает, не переписывает** код и не «дочиняет» коробку на живую. Любая реорганизация — отдельная осознанная работа потом.
- **Молчаливый дрейф фундамента.** Пропустить обновление фундамента в конце задачи или никогда не прунить. Устаревший фундамент — баг.
- **Слепой `git add .`** на папке с секретами и данными (см. главу про git).

## 6. Внедрение в существующий проект (`/onboard`)

Остальная семья предполагает «чистое поле»: решили → задокументировали → построили.
`/onboard` едет в обратную сторону — для того, что у тебя уже есть: код, написанный
до этой дисциплины, или коробка, развёрнутая до неё. Это **одноразовый** акт; после
него проект — обычный гражданин, и его дальше ведут реактивные сессии, доска задач и `/prune`.

**Какие секции запускать** (тот же вопрос, что и в дизайн-сессии):

- есть **мой код** → Секция 1;
- есть **развёрнутая коробка** → Секция 2;
- и то, и другое → обе;
- чистый готовый сервис, развёрнутый давно (n8n, Postgres) → только Секция 2 (получит паспорт, без фундамента кода).

**Секция 1 — фундамент из существующего кода.** Агент **обнаруживает фактическую структуру, а не навязывает стандартную**. Он не ждёт `src/`: код может лежать плоско в корне, под одной или несколькими app-папками, вразброс. Агент инвентаризирует дерево, классифицирует (код / конфиг / данные / логи / доки / тесты / мусор) и ориентируется по тому, **что реально запускается** (entrypoints, манифесты зависимостей), а не по именам папок. Затем выводит лёгкий фундамент: `ARCHITECTURE.md` описывает layout **как он есть** (компоненты — концептуально, не пофайлово); `CONVENTIONS.md` фиксирует конвенции, которым код **уже следует**; `DECISIONS.md` стартует почти пустым с одной записью `## <дата> — onboarded` — историю прошлых решений агент **не выдумывает**.

**Что агент выносит тебе на разрешение** (код этого сам не покажет — решаешь ты):

- параллельные/дублирующиеся компоненты (две backend-папки) — что живое, что мёртвое;
- версионированные имена (`foo_v3_5.py` рядом со старыми) — что актуально;
- кладбища мёртвого кода (`trash/`, `old/`) — исключить из карты;
- чужие доки (`*.md`, `docs/`) — это **вход, не истина**; читаем, но что ещё верно — решаешь ты;
- уже существующую папку `ai/` — агент её **не затирает**, а осторожно сверяет.

**Секция 2 — паспорт из живой коробки.** Агент читает реальность только на чтение
(`docker-compose.yml`, `.env` с маскировкой, `sudo docker ps`, `sudo ss -tlnp`),
выводит `STACK.md` и **честно заносит нарушения старого деплоя** (сеть `bridge`, порт БД
на `0.0.0.0`, контейнер от root, нет compose-файла) в раздел «Deviations / legacy risks»
с пометкой «принято» или «надо исправить». **Он не чинит работающий стек.** Исправление —
это потом, по одному риску за раз, через `docker-deploy`, с его стоп-сигналами.

> **Главное про онбординг:** он **документирует и ратифицирует настоящее**, а не
> переделывает его. И именно здесь — самый опасный момент работы с git (следующая глава):
> папка уже набита `.env`, `data/`, `__pycache__` и бэкап-архивами, и слепой первый коммит
> утащит секреты и гигабайты в историю.

> **Пример.** Открыл старый проект: код плоско в корне, рядом папка `trash/` и каталог
> `backend_v2/` при живом `backend/`. Запускаешь `/onboard` на сильной модели. Агент строит
> карту, спрашивает: «`trash/` — выкинуть из карты? `backend_v2/` — это живое или брошенная
> попытка?». Ты отвечаешь, он документирует layout как есть, ставит `ai/` и git-базу, **ничего
> не переименовав**. Захочешь убрать `backend_v2/` — это уже отдельная работа потом.

## 7. Git с нуля

Это самая важная глава, и она написана, чтобы **снять страх**, а не добавить его.

### Что такое git — в одну фразу

> Для тебя git — это **кнопка «сохранить», кнопка «отменить» и машина времени для всего
> проекта сразу.** Не «система контроля версий», не «инструмент для команд». Кнопка, кнопка,
> машина времени.

### Чего в твоём контуре НЕ существует

Половина страха перед git — от слов, которых ты никогда не встретишь. В твоей работе
**нет и не будет**: веток, слияний (merge), rebase, cherry-pick, конфликтов, force-push,
`reset --hard`. Если где-то увидишь эти слова — это не про тебя. Ты работаешь в одну
прямую линию сохранений, и всё.

### Эмоциональный замок

> **Закоммиченное (сохранённое) потерять нельзя.** Пока ты пользуешься только набором
> команд ниже, вся работа git сводится к одному: гарантировать, что ты **всегда можешь
> вернуться к рабочему состоянию**. Сломать необратимо то, что уже сохранено, этими
> командами невозможно.

### Реальный режим: коммитит агент, не ты

В обычной жизни ты git почти не трогаешь. **Рутину коммитит агент сам** — при постановке и закрытии задачи,
на каждом законченном куске реактивной работы, в конце `/prune` и `/onboard`. Каждая из этих команд заканчивается коммитом,
то есть очередной точкой сохранения. Твои руки нужны git только в двух случаях: один раз
настроить его на машине, и в редкий момент паники (аварийный набор ниже).

### Аварийный набор (выучи только эти пять)

```bash
git status          # где я и что изменилось с последнего сохранения. ВСЕГДА первая команда.
git log --oneline   # список точек сохранения, по строке на каждую, новые сверху.
git diff            # что именно поменялось в файлах (ещё не сохранённое).
git restore .       # выбросить НЕсохранённые изменения и вернуться к последнему сохранению.
git revert <hash>   # безопасно отменить УЖЕ сохранённое плохое (создаёт новый коммит).
```

Подробнее, простыми словами:

- **`git status`** — «где я нахожусь и что поменялось». С неё начинается любой разбор.
- **`git log --oneline`** — список твоих точек сохранения. `<hash>` — это короткий код слева
  в каждой строке; им ты адресуешь конкретную точку.
- **`git diff`** — показывает построчно, что изменилось с последнего сохранения, но ещё не
  сохранено. Полезно глянуть перед тем, как соглашаться на коммит.
- **`git restore .`** — «выкинуть весь несохранённый мусор и вернуть файлы к последнему
  сохранению». Это для «агент напортачил, я ещё не коммитил». *Тонкость:* если агент создал
  совсем новые файлы, git их пока не отслеживает — `restore` их не уберёт; такие просто
  удали вручную или попроси агента.
- **`git revert <hash>`** — «безопасно отменить уже сохранённое плохое». Создаёт **новый**
  коммит, который откатывает изменения указанного. Ничего не уничтожает, история цела —
  поэтому это безопасно. `<hash>` берёшь из `git log --oneline`.

> **Почему здесь НЕТ `reset --hard`.** Это единственная ходовая команда, которая умеет
> **необратимо** выбросить уже сохранённую работу и сделать твой эмоциональный замок
> неправдой. Тебе она не нужна ни разу: всё, что делает `reset --hard` «хорошего», безопасно
> делают `git restore` (для несохранённого) и `git revert` (для сохранённого). Если когда-нибудь
> почувствуешь, что «надо `reset --hard`» — это сигнал остановиться и позвать агента, а не жать.

### Настройка с нуля (один раз на машине)

```bash
git --version                                   # есть ли git вообще
# если нет, на Debian/Ubuntu:  sudo apt install git
git config --global user.name  "Твоё Имя"       # кто автор коммитов
git config --global user.email "you@example.com"
```

И в папке проекта (это обычно делает агент в `bootstrap`/`onboard`, но вот что под капотом):

```bash
cd /путь/к/проекту
git init               # завести машину времени в этой папке
# создать .gitignore (см. ниже) — ОБЯЗАТЕЛЬНО до первого add
git status             # посмотреть, что git собирается взять
git add .              # взять файлы под учёт — только ПОСЛЕ проверки .gitignore и status
git commit -m "initial"   # первая точка сохранения
```

`.gitignore` — список того, что git должен **игнорировать** (никогда не сохранять).
Минимум:

```gitignore
# секреты и данные — НИКОГДА в git
.env
.env.*
data/

# воспроизводимые зависимости (ставятся заново, в истории не нужны)
node_modules/
venv/
.venv/
__pycache__/

# бэкап-архивы
*.tar.gz
*.zip
*.bak
```

### Самый опасный момент: git-база при `/onboard`

Когда ты заводишь под git **старую** папку, она уже набита `.env`, `data/`, `__pycache__`
и бэкап-архивами. Слепой `git add .` утащит секреты и гигабайты в историю — а из истории
их потом вычищать больно. Поэтому ритм здесь **жёсткий и без исключений**:

```
1. сначала .gitignore   →   2. git status   →   3. глазами проверь, что в коммит
   НЕ попадают .env, data/, архивы   →   4. только теперь коммит
```

> **Никогда не делай `git add .` на онбординге, не посмотрев глазами `git status`.**
> Это единственный шаг во всей системе, где ошибка стоит дорого, и единственный, где агенту
> предписано остановиться и показать тебе список перед первым коммитом. Подтверждаешь — ты.

### Связь с системой

- **Карточки задач не протухают по git.** В карточке нет снимка кода — только намерение,
  дата постановки и, у подзадачи, ссылка на проект. Поэтому и проверять её против HEAD
  нечего: стареет она по календарю, и агент, беря задачу старше месяца, спрашивает, нужна ли
  она ещё. Ставит, закрывает и сохраняет карточку глагол — `fraim task-new` / `fraim task-seal`.
- **Каждая рабочая команда заканчивается коммитом:** постановка и закрытие задачи, `/prune`, `/onboard`,
  и каждый законченный кусок реактивной сессии. То есть после любой завершённой работы у тебя есть свежая точка возврата —
  без твоего участия.

### Копия вне машины (`fraim publish`)

Пока проект живёт на одном диске, он существует только для тебя, сидящего за этой машиной.
Облачная сессия, CI, второй компьютер, агент в вебе — все они начинают с клонирования, и
того, чего нет на хосте, для них **нет вовсе**. Это не про бэкап (данных в истории и так
нет) — это про досягаемость.

Одна команда, и она же — пункт меню «Копия вне машины»:

```sh
fraim publish
```

**Что она спросит.** Ровно две вещи, потому что правильный ответ на них у разных людей
разный, и он твой:

1. **Где хранить.** GitHub (через `gh`), GitLab (через `glab`) или **любой другой хост по
   ссылке** — Gitea, Codeberg, Bitbucket, свой сервер. Рядом с каждым вариантом написано,
   можно ли им воспользоваться прямо сейчас; по умолчанию предлагается первый готовый.
2. **Кто сможет читать.** Приватный или публичный. **По умолчанию приватный**, и публичным
   репозиторий не станет от того, что ты нажал Enter, — только явным выбором в меню или
   флагом `--public`.

**Что она сделает сама** (и в чём весь смысл): проверит, чем можно опубликовать; если чего-то
не хватает — покажет строчку установки под твою систему, а не «установите GitHub CLI»; создаст
репозиторий; пропишет адрес; отправит; **сверит, что на хосте лежит ровно то же, что здесь**.
Последнее не украшение: push умеет отчитаться об успехе там, где хост тихо ничего не принял.

**Ничего не поставлено — не тупик.** Провайдерский CLI это ускоритель, а не требование. Пол
всегда один и тот же: создай пустой репозиторий в браузере и дай ссылку.

```sh
fraim publish --url git@github.com:имя/проект.git
```

#### Адрес и доступ — разные вещи

`git@host:…` требует ssh-ключа на хосте, `https://host/…` — логина. Это два разных
доступа, и наличие одного ничего не говорит о другом: `gh auth login` с протоколом HTTPS
учит git брать логин для https и **не кладёт ssh-ключ**.

Поэтому, если хост отказал по ключу (`Permission denied (publickey)`), а вход `gh` для
https уже есть, публикация **сама переключает адрес на https того же репозитория** —
вслух, с записью в ремоут. Хост, имя, видимость и ветка не меняются: ратифицированный
репозиторий остаётся тем же, меняется только транспорт. Если переключить нечем, команда
называет оба рабочих выхода — готовый https-адрес и как положить ключ на хост, — а не
советует ещё раз то, что уже не помогло.

#### Проверка безопасности — до отправки, а не после

Публикация необратима: то, что уехало на хост, оттуда уже не отозвать. Поэтому перед планом
всегда идёт проверка того, **что именно уедет**, — и смотрит она в историю, а не в папку.
Файл, удалённый из дерева месяц назад, лежит в истории и уезжает с первым же `push`.

| Находка | Что делает |
|---|---|
| `.env`, ключи, `id_rsa`, `.pem`, `credentials.json`, `.npmrc` в истории | **решает видимость** — см. ниже |
| токен по форме (GitHub, GitLab, AWS, Slack, Google, ключи API) в текущем снимке | **решает видимость** — см. ниже |
| `node_modules/`, `venv/` в истории; файлы тяжелее 5 МБ; базы и дампы | показывает и пропускает |
| `.env` лежит в папке и не закрыт `.gitignore` | показывает и пропускает |

Границу проверка называет вслух и не изображает большего: **имена** сверяются по всей истории,
**содержимое** — в текущем снимке. Полный обход истории по содержимому это другой инструмент и
другое время работы. Значение найденного ключа **никогда не печатается** — только файл и
строка: вывод уезжает в скроллбек, в лог сессии и в чужой чат.

#### Решает не находка, а то, кто её прочитает

Цена утечки ключа целиком зависит от того, кто сможет его открыть, — поэтому одинаковый ответ
на публичный и приватный репозиторий неверен в обе стороны. Правило простое:

| Куда едет | Что происходит с находкой |
|---|---|
| **публичный** репозиторий | стоп. Варианта «приму риск» нет: принимать его пришлось бы не тебе одному |
| **приватный** репозиторий | находки названы поимённо, и ты принимаешь их отдельным «да». Работа не встаёт |
| видимость неизвестна | стоп, но с выходом: скажи явно `--private` или ответь на вопрос в терминале |

Приватность берётся в таком порядке: сначала то, что можно проверить (репозиторий создаём мы —
значит знаем; GitHub через `gh` спрашивается напрямую), и только потом то, что сказал ты. Если
хост отвечает «публичный», твоё `--private` его не перебивает.

Принятие риска говорится вслух и каждый раз — это не настройка и не флаг «больше не спрашивай»:

```
! 1 находка уедет в приватную копию как есть — принято
  приватность известна: с твоих слов
  чего это не отменяет: ключ увидят все, у кого есть доступ к репозиторию, и он
  останется в истории, если репозиторий когда-нибудь станет публичным
  вычистить, а не принимать — ответь «нет»: команда отдаст задание агенту

  Публикуем ВМЕСТЕ с находками в приватную копию? [y/N]
```

Обещания «в приватном ничего не страшно» здесь нет намеренно: приватный репозиторий
переключается в публичный одной кнопкой, и история едет вместе с ним. Но решение твоё, и
продукт не встаёт у тебя на пути.

**«Нет» здесь означает «хочу, но чистым»** — и обрабатывается именно так. Это единственное
место, где человек уже понял проблему и упёрся в операцию, которой у системы нет: убрать файл
из истории значит её переписать. Поэтому вместо слова «отменено» команда печатает то же
задание для агента, что и при своём собственном отказе, — с находками внутри, с границами
(не публиковать, не пушить, `--force` не предлагать) и с тем, чем проверить результат:

```
  Отменено — публикуем после чистки.
  1 находка остаётся в истории. Убрать её оттуда — значит переписать историю,
  а это единственная операция, которую система себе не позволяет: работа для агента.

  Отдай это агенту — скопируй всё между линиями:
  ────────────────────────────────────────────────────────────────
  …
  ────────────────────────────────────────────────────────────────

  когда агент отчитается — проверь сам: fraim publish --check должен сказать «чисто»,
  и тогда fraim publish отправит копию уже без находок
```

То же задание печатается и по требованию, без отказа — приняв риск однажды, чистку
обычно заказывают позже:

```sh
fraim publish --brief
```

А если находка просто ложная (тестовая фикстура, пример в документации) — обход есть и он
виден, независимо от видимости:

```sh
fraim publish --force     # скажет вслух, что находки уедут и это необратимо
```

#### Когда копия есть только на словах

Самое неприятное состояние — не «копии нет», а «копия есть, но пустая»: репозиторий на хосте
создан, адрес прописан, а история туда не доехала. Снаружи всё выглядит сделанным, и человек
живёт с уверенностью, что проект доступен откуда угодно. Так же выглядит ветка, снесённая на
хосте после отправки: локальные записи по-прежнему говорят «всё уехало», потому что это память
**этой машины** о прошлом push, а не правда с хоста.

Поэтому проверяется в двух местах, и границы у них разные:

| Кто | С сетью | Что видит |
|---|---|---|
| сторож (`fraim status`, меню) | нет | адрес прописан, но туда **ни разу ничего не уезжало** — настройку начали и не довели |
| `fraim publish --check` | нет | то же самое плюс что уедет и нет ли секретов; честно говорит, что хост не спрашивал |
| `fraim publish` | да | **правду с хоста**: там пусто / там старее / там ровно то же / там есть чужая работа |

Строка «на хосте» стоит прямо в плане, до вопроса «публикуем?». Если репозиторий пуст или
отстал — та же команда доводит дело до конца, ничего доделывать руками не нужно.

Отдельный случай — **на хосте есть работа, которой нет здесь** (вторая машина, веб-сессия, CI,
второй человек). Здесь команда останавливается и не предлагает никакой кнопки: любой способ
свести это «одним нажатием» затирает чью-то работу. Вместо совета она печатает готовое задание
агенту — с адресом, веткой, обоими коммитами и запретом на force-push.

#### Когда отправлять нельзя: готовое задание вместо совета

Сказать «убери файл из истории и повтори» — значит потребовать экспертизы, которой у тебя может
не быть. Поэтому там, где команда всё-таки останавливается — публичный репозиторий с находкой и
расхождение с хостом, — она печатает **блок, который копируешь целиком и отдаёшь агенту**: путь проекта, что именно найдено (поимённо),
порядок работы и границы, за которые агенту выходить нельзя («ничего не пушить», «`--force` не
предлагать», «не запускать без моего „да“»).

Первым шагом там всегда стоит не git, а **смена самого ключа**: он уже полежал в файле, и
никакая чистка истории этого не отменяет. А чистка истории — это её переписывание, единственная
операция, которую система себе не позволяет нигде (`fraim undo` откатывает встречным коммитом
именно поэтому). Значит это честно чужая работа, и продукт отдаёт её так, чтобы её можно было
просто заказать.

#### Дальше

Та же команда отправляет следующие точки сохранения — `fraim publish` на проекте с уже
настроенной копией просто досылает то, что не уехало, с той же проверкой перед отправкой.
Если всё на месте, она так и говорит и ничего не делает.

Разведка без единого сетевого вызова — `fraim publish --check`: чем можно опубликовать, есть
ли копия, доводили ли настройку до конца, что нашла проверка безопасности. Хост он не
спрашивает и об этом говорит вслух — правда с хоста стоит одного сетевого вызова, и его делает
`fraim publish`. Это же режим для агента: посмотреть и рассказать он может, отправку начинает
человек.

### Мини-плейбук паники (git)

- **Агент напортачил, я ещё НЕ сохранял** (не было коммита после) → `git restore .`
- **Напортачил, и это УЖЕ сохранено** → `git log --oneline`, найди плохой коммит, `git revert <hash>`
- **Совсем потерялся** → `git status` (где я) → `git log --oneline` (куда вернуться) → найди
  последний хороший коммит → попроси агента безопасно вернуть к нему. Ничего не жми наугад.

## 8. Ритм обслуживания

Дрейф — это медленное расхождение документов с кодом: реактивные сессии поменяли поведение,
само-отчёты задач никто не перепроверял, `DECISIONS` распух, `ARCHITECTURE` описывает
то, чего уже нет. Лечится `/prune`. Когда запускать:

- **когда сторож сказал, что фундамент отстал**, ИЛИ
- **раз в 2–4 недели**, по календарю.

**Как считается дрейф.** Сторож берёт последний коммит, тронувший `ARCHITECTURE.md`, и считает,
сколько коммитов кода легло после него; порог — `foundation_lag_commits`. Счётчик сбрасывают
два якоря, побеждает ближний: сама карта сдвинулась, либо прошёл `/prune`. Считаются коммиты,
а не дни — сотня коммитов за две недели это дрейф, а один коммит через месяц — нет.

**Как замечать, не вспоминая.** Не держи это в голове — для этого есть `/orient`. Вернулся
в проект, запустил `/orient`, и в блоке «Foundation health» он сам скажет: *«N коммитов кода
с последнего обновления ARCHITECTURE.md — фундамент мог поплыть, запусти `/prune`»*, либо отметит замеченную
нестыковку (компонент в `ARCHITECTURE`, которого нет в коде; карточка, висящая месяцами).
То есть рабочий цикл такой: **возвращаешься → `/orient` → он говорит, нужен ли `/prune`.**

## 9. Плейбук восстановления: «что-то сломалось»

Спокойно, по строкам. Найди свою ситуацию.

| Симптом | Что делать |
|---|---|
| Агент наизменял, я ещё **не коммитил** | `git restore .` — откат к последнему сохранению. |
| Агент наизменял, и это **уже закоммичено** | `git log --oneline` → найди плохой коммит → `git revert <hash>`. |
| **Совсем потерялся** в проекте | `git status`, потом `git log --oneline`, найди последний хороший коммит, позови агента вернуть к нему. |
| Не помню, **где остановился** | `/orient` — он прочтёт фундамент, доску и историю и скажет следующий шаг. |
| Документы **разошлись с кодом** (`ARCHITECTURE` врёт) | `/prune` (сильная модель) — он предложит диффы, ты одобряешь. Противоречие код↔решение он вынесет тебе как развилку. |
| Открыл **старый проект/коробку** без фундамента | `/onboard` (сильная модель), один раз. Дальше — обычная петля. |
