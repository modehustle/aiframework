# README.md — как водить систему

> Твоя личная настольная инструкция. Ты один управляешь разработкой на AI-агентах,
> и бываешь то планировщиком, то исполнителем. Этот файл — про то, как держать контур:
> что запускать в какой ситуации, на какой модели, что делаешь ты и что делает агент,
> и как не бояться git. Читай по делу, не подряд: открыл нужный раздел — сделал.

## 0. Установка

**Если репозиторий публичный:**

```sh
curl -fsSL https://raw.githubusercontent.com/modehustle/aiframework/main/installer/install.sh | sh
fraim init
```

**Если репозиторий приватный**, однострочник не сработает: `raw.githubusercontent.com` отдаёт
на приватный репозиторий 404 без токена. Клонируй тем доступом, который у тебя уже есть, —
установщик подхватит готовый клон и дальше будет обновлять его сам:

```sh
git clone git@github.com:modehustle/aiframework ~/.fraim/src   # или https://, как удобнее
sh ~/.fraim/src/installer/install.sh
fraim init
```

`fraim init` находит установленные харнесы (Hermes, Claude Code, Codex, omp, pi, Devin CLI),
раскладывает по ним 12 процедур и мастер-скилл как Agent Skills, дописывает контекстный блок
в их `AGENTS.md` и заводит реестр проектов. Команда **идемпотентна**: она же обновление, она же
подключение только что поставленного харнеса. Устаревшие скиллы прошлых версий она убирает
сама, чужие — не трогает.

Поставить не `main`, а конкретную ветку (например, чтобы проверить неслитый PR):

```sh
FRAIM_BRANCH=имя-ветки sh ~/.fraim/src/installer/install.sh
```

Для Claude Code есть и плагин — тогда обновления приезжают штатным каналом. Это путь для
**публичного** репозитория; на приватном ставь через `install.sh` выше:

```
/plugin marketplace add modehustle/aiframework
/plugin install fraim
```

Проверить, что получилось: `fraim doctor`.

Вернувшись в проект, спроси сторожа — он детерминированный, без модели и без сети,
так что звать его можно сколько угодно:

```sh
fraim status
```

```
payments-api
  ! 23 коммита кода с последнего обновления ARCHITECTURE.md → /prune
  ! задача «add-auth» заблокирована 9 дней назад     → /revise-task
  · 2 задачи в очереди                               → /run-task
```

Завести проект под систему:

```sh
cd ~/projects/payments-api
fraim scaffold        # разворачивает фундамент и ai/, ничего не перезаписывая
```

Дальше `/bootstrap` (новый проект) или `/onboard` (код, написанный до системы) заполняют
развёрнутые файлы. Пока они не заполнены, сторож честно говорит «скелет развёрнут, но не
заполнен» — пустой фундамент никогда не изображает здоровье.

**Git знать не нужно.** Каждая точка сохранения здесь — коммит, поэтому репозиторий это часть
скелета: `fraim scaffold` заводит его, если его нет (внутри чужого — никогда). Дальше точки
ставят сами процедуры, а вернуться к любой можно, не зная ни одной команды git:

```sh
fraim undo            # показывает точки, поставленные системой
fraim undo a1b2c3d    # отменяет одну — встречным коммитом, историю не переписывая
```

Сторож заодно замечает то, чего git сам не скажет: что удалённой копии нет вовсе или что
точки сохранения с этой машины не уезжали. Это **не про бэкап** — это про досягаемость:
облачный агент, CI и вторая машина начинают с клонирования, и того, что осталось на диске,
для них не существует. Завести копию сторож не пытается — где её держать и какой она должна
быть, решаешь ты вместе с агентом.

Ни одна процедура не попросит тебя выполнить git-команду. И ни один глагол не умеет «сохранить
всё»: сохраняются ровно те пути, которые он сам изменил, — поэтому `.env`, данные и твоя
незаконченная работа не уезжают в историю, и никому не приходится за этим следить.

Настройки — на двух уровнях, `fraim config` показывает не файл, а что действует и откуда:

```
  foundation_lag_commits 20     ← ai/fraim.conf
  foundation_lag_commits 20     ← ~/.fraim/config
  stale_plan_commits     1      ← по умолчанию
```

Подробности установки и устройство — [installer/README.md](installer/README.md).
Почему механика отдана CLI, а не модели — [installer/DETERMINISM.md](installer/DETERMINISM.md).
По каким правилам принимаются такие решения — [PRINCIPLES.md](PRINCIPLES.md).
Что найдено, но отложено — [BACKLOG.md](BACKLOG.md).
Последний дизайн-проход по находкам эксплуатации — [DESIGN-2026-09.md](DESIGN-2026-09.md).
Последний прогон чек-листа по всем процедурам — [AUDIT-VERBS.md](AUDIT-VERBS.md).

## 1. Зачем это всё и как оно устроено

Агенты сильны, но забывчивы: они дрейфуют, теряют контекст между чатами и любят
импровизировать. Система воркфлоу-команд лечит ровно это. Она оставляет в каждом
проекте **постоянный контекст** и ставит агенту **жёсткие рельсы**, чтобы ты в одиночку
вёл весь жизненный цикл и мог вернуться в проект через две недели, ничего не угадывая.

**Фундамент** — это всегда-актуальный контекст проекта, набор файлов в его корне:

- `ARCHITECTURE.md` — карта проекта (что это, компоненты, модель данных, интерфейсы).
- `CONVENTIONS.md` — правила дома: как тут работают + раздел `## Known Pitfalls / Lessons`
  (грабли, на которые уже наступали).
- `DECISIONS.md` — журнал решений, **только дописывается** (новое сверху, старое не стирается).
- `ai/` — рабочая папка петли: очередь задач, архив, расследования.
- `STACK.md` — паспорт коробки (появляется, если проект развёрнут в Docker).
- `AGENTS.md` (+ `CLAUDE.md`-указатель) — правила проекта **для любого агента**, который его
  откроет. Фундамент едет в репозитории, и с этим файлом инструкция читать его едет вместе с
  ним: облачная сессия, CI, вторая машина или чужой харнес узнают правила из самого репозитория,
  а не из настроек твоего ноутбука.

> **Инвариант 0.4 — золотое правило.** `ARCHITECTURE.md` и `CONVENTIONS.md` читаются
> ПЕРВЫМ делом перед любой задачей и обновляются ПОСЛЕДНИМ шагом, без напоминания.
> `DECISIONS.md` — append-only. Устаревший фундамент считается багом, а не косметикой.

**Роли** (ты переключаешься между ними сам):

- **Планировщик** — решает, что делать, и пишет точный план. Команды: `/make-task`, `/revise-task`.
- **Исполнитель** — исполняет план дословно. Команда: `/run-task`.
- **Садовник** — периодически сводит документы с реальностью. Команда: `/prune`.
- Плюс **разведчик** (только чтение, для возврата): `/orient`.

Но чаще всего никакой роли нет: **реактивная сессия** — вопрос, мелкая правка, изменение,
форма которого проявилась по ходу — это самый частый режим, и он законный.

**Петля для нового проекта (greenfield):**

```
design-session  →  bootstrap  →  (deploy)  →  [ make-task → run-task → archive ]*
                                                    ↑ реактивные сессии / orient / revise / prune по ходу
```

**Он-рамп для уже существующего:** `/onboard` — едет в обратную сторону, одноразово,
после чего проект встаёт в обычную петлю.

Одна фраза «зачем» на каждый слой:

| Слой | Зачем |
|---|---|
| `design-session` | решить, ЧТО и ПОЧЕМУ строим — до того как появилась папка, код, контейнер |
| `bootstrap` | заложить фундамент кода, чтобы возвращаться с контекстом, а не угадывать |
| `deploy` | упаковать в безопасную Docker-коробку и написать её паспорт |
| `/make-task` | зафиксировать согласованный план так, чтобы чужой (и дешёвый) агент исполнил его |
| `/run-task` | исполнить план дословно и проверить |
| `/revise-task` | починить план, который исполнитель признал кривым, не теряя находок |
| реактивная сессия | сделать работу здесь и сейчас, без церемоний — режим по умолчанию |
| `/prune` | свести документы с реальностью, пока дрейф не сгнил |
| `/orient` | вернуться после паузы и понять, где всё стоит |
| `/expose` | впустить трафик к развёрнутому: прокси, сертификат, файрвол |
| `/onboard` | завести под систему то, что существовало до неё |

## 2. Дерево решений: «хочу X → что запускать»

Открыл таблицу, нашёл свою строку, запустил. Если в таблице нет твоей строки — это
нормально: значит это обычная реактивная сессия, работай без процедуры.

| Ситуация | Что запускать | Модель |
|---|---|---|
| Новый проект с нуля, ещё ничего нет | `design-session` → `bootstrap` → (`deploy`) | сильная |
| Готовый сервис без своего кода (n8n, Postgres, Redis) | `design-session` (короткий) → `deploy`. **НЕ** bootstrap | сильная / deploy — способная |
| Уже есть **мой код**, написанный ДО системы | `/onboard` (Секция 1). **НЕ** bootstrap | сильная |
| Уже есть **развёрнутая коробка** ДО системы | `/onboard` (Секция 2). **НЕ** deploy | сильная |
| И код, и коробка из прошлого | `/onboard` (обе секции) | сильная |
| Новая фича или заметное изменение | `/make-task` → `/run-task` | make — сильная, run — дешёвая |
| Правка, которую делаешь сам, здесь и сейчас | ничего не запускать — реактивная сессия | любая |
| Работу надо отдать другому чату / дешёвой модели | `/make-task` → `/run-task` | make — сильная |
| Вернулся после паузы, не помню статус | `/orient` | любая |
| Исполнитель сказал «план невыполним» (появился `blockers.md`) | `/revise-task` → потом `/run-task` | сильная |
| Фундамент поплыл (сторож сказал про отставание) | `/prune` | сильная |
| Надо развернуть то, что собрал | `/docker-deploy` | способная |
| Развёрнутое надо сделать доступным снаружи | `/expose` | способная |

## 3. Шпаргалка по командам

По одной карточке на команду: **что · когда · модель · ты · агент · конец**.

### `design-session` — парадная дверь
- **Что:** думательная сессия. Решаем ЧТО строим и ПОЧЕМУ — до папки, кода и контейнера. Агент тут партнёр по размышлению, **не строитель**.
- **Когда:** самый старт нового дела.
- **Модель:** сильная.
- **Ты:** отвечаешь на вопросы, выбираешь из альтернатив, подтверждаешь финал.
- **Агент:** рамкирует задачу, раскладывает варианты, сводит к одному решению (с обоснованием и отвергнутыми альтернативами); ничего не создаёт, кроме одного артефакта.
- **Конец:** один артефакт — **Design Brief** (если это твой код) или **per-stack prompt** (если готовый сервис). С ним идёшь дальше.

### `bootstrap` — фундамент кода
- **Что:** кладёт фундамент авторского проекта: foundation-файлы + минимальный рабочий скелет кода.
- **Когда:** после `design-session`, для проекта со своим кодом.
- **Модель:** сильная.
- **Ты:** подтверждаешь дизайн (без «да» агент не пишет код), смотришь сгенерированные файлы.
- **Агент:** валидирует Design Brief; генерирует `README` / `ARCHITECTURE` / `CONVENTIONS` / `DECISIONS` + `.gitignore` + `.env.example` + `ai/`; затем скелет с entrypoint и health-эндпоинтом.
- **Конец:** фундамент стоит. Дальше `deploy` (когда есть что запускать) и петля make/run.

### `deploy` — коробка + паспорт
- **Что:** безопасно упаковывает стек в Docker и пишет паспорт `STACK.md`.
- **Когда:** когда есть что запускать (рано — для dev-коробки, поздно — когда есть функциональность).
- **Модель:** способная (механика + стоп-сигналы безопасности).
- **Ты:** вводишь хостовые пароли сам; подтверждаешь открытие портов; применяешь то, что пишется в `/etc` (nginx, certbot) — это хостовые действия, агент их не делает.
- **Агент:** выбирает режим доступа A/B/C, генерирует `compose` / `.env` / конфиги, проверяет, что наружу не торчит лишнее, пишет `STACK.md`; на хостовых шагах — стоп и просит тебя.
- **Конец:** запущенная защищённая коробка + `STACK.md`.

### `/make-task` — планировщик
- **Что:** сериализует согласованный план в новую папку `ai/tasks/<slug>/` (`context.md` + `task.md`), чтобы другой агент в **чистом чате** исполнил его без этого разговора.
- **Когда:** вы с агентом договорились о фиче/изменении.
- **Модель:** сильная.
- **Ты:** обсуждаешь план, потом запускаешь `/make-task`.
- **Агент:** читает фундамент; если трогается существующий код — делает **reference scan** (карту всех зависимостей, чтобы исполнитель не спотыкался); пишет самодостаточный план «под пол» (под самого слабого исполнителя).
- **Конец:** *«Готово. Открой новый чат и запусти `/run-task`.»*

### `/run-task` — исполнитель
- **Что:** берёт задачу из очереди, исполняет **дословно**, проверяет, обновляет фундамент, **пишет `result.md` и коммитит**; архивирует — отдельно, по твоей команде.
- **Когда:** в очереди есть готовая (не заблокированная) задача.
- **Модель:** дешёвая по умолчанию; для сложной/комплексной задачи подними до Sonnet или Opus.
- **Ты:** запускаешь, читаешь отчёт, говоришь «да»/«нет»; когда захочешь — просишь заархивировать (в этом или новом чате).
- **Агент:** грузит фундамент и контекст; делает sanity- и staleness-проверку; исполняет шаги строго в рамках `Files to Change`; ничего лишнего не трогает; verify; обновляет `ARCHITECTURE`/`DECISIONS`; **пишет отчёт в `ai/tasks/<slug>/result.md` (не только в чат) и делает безусловный коммит — точку сохранения, до твоего «да»**. **Если план кривой — пишет `blockers.md` и СТОП**, а не чинит сам.
- **Конец:** отчёт (файл + копия в чат) + свежий коммит + *«Принимаем результат?»*. На «да» — заносит грабли в `CONVENTIONS` (по твоему согласию, отдельным коммитом) и ждёт твоей команды на архив. Архив — отдельный шаг: перенос папки в `ai/archive/` + коммит.

### `/revise-task` — планировщик чинит план
- **Что:** чинит кривой план **на месте** (amend, не заново), сохраняя то, что исполнитель уже выяснил.
- **Когда:** в задаче появился `blockers.md`.
- **Модель:** сильная (это работа планировщика).
- **Ты:** запускаешь `/revise-task`, обсуждаешь диагноз.
- **Агент:** читает `blockers.md` + план, диагностирует с тобой, правит `context.md`/`task.md` на месте, ставит пометку `## Revision N`, обновляет provenance-штамп, удаляет отработанный `blockers.md`.
- **Конец:** *«План починен. Запусти `/run-task` снова.»*

### Реактивная сессия — режим по умолчанию
- **Что:** обычная работа с агентом без всякой процедуры. Никакой команды запускать не надо.
- **Когда:** чаще всего. Вопрос, мелкая правка, разбор, изменение, форма которого проявилась по ходу.
- **Потолка нет.** Размер не важен: пока ты в сессии и решаешь сам — это законный режим,
  и загонять его в `/make-task` не надо.
- **Что всё равно держится:**
  фундамент читается первым и правится последним (инвариант 0.4) ·
  поменялось поведение → строка в `DECISIONS.md` ·
  **точка сохранения на каждый законченный кусок**, а не в конце сессии — сессия может умереть.
- **Точка сохранения:** `fraim commit fix "<что изменилось>" <путь> <путь>`. Эти коммиты **и есть**
  запись реактивной работы, отдельного журнала нет.
- **Когда всё-таки `/make-task`:** не когда «стало большим», а когда работу надо **отдать**
  тому, кого нет в этом разговоре — новому чату, дешёвой модели, завтрашнему себе.

### `/prune` — садовник
- **Что:** сверяет фундамент с реальностью и **предлагает диффы** — сам не переписывает. Истина — код, не документы.
- **Когда:** когда сторож сказал, что фундамент отстал от кода, ИЛИ раз в 2–4 недели.
- **Модель:** сильная.
- **Ты:** одобряешь / правишь / пропускаешь каждый дифф; решаешь развилки (прав код или прав документ).
- **Агент:** Секция 1 (код → `ARCHITECTURE`/`CONVENTIONS`/`DECISIONS`), Секция 2 (`compose` + живое состояние → `STACK.md`); устаревшие записи `DECISIONS` **переносит** в `ai/archive/decisions_log.md` (не удаляет); противоречие код↔решение — **флагует как развилку**, сам не чинит; отмечает прунинг коммитом.
- **Конец:** что изменилось, сколько решений ушло в архив, и какие развилки оставлены тебе (возможные баги → `/make-task`).

### `/orient` — вернуться с контекстом
- **Что:** строго **читает** — грузит фундамент и говорит, где всё стоит и что делать дальше. Ничего не меняет.
- **Когда:** вернулся в проект после паузы / в свежем чате.
- **Модель:** любая (лёгкая, read-only).
- **Ты:** читаешь сводку, выбираешь следующий шаг.
- **Агент:** первым делом спрашивает сторожа (`fraim status --json`), затем читает `ARCHITECTURE`/`CONVENTIONS`/`DECISIONS`/`STACK`/`README` + очередь задач; даёт сжатую сводку (что за проект · очередь · недавняя история · здоровье фундамента) и называет **один** следующий шаг.
- **Конец:** рекомендация команды. Сам работу не начинает.

### `/onboard` — он-рамп для существующего
- **Что:** заводит под систему то, что было ДО неё. Обратный bootstrap/deploy: **реальность → выведенные из неё документы → ратификация тобой**. Одноразово. **Неразрушающе** (код не двигается).
- **Когда:** открыл старый проект или коробку, у которых нет фундамента/паспорта.
- **Модель:** сильная.
- **Ты:** разрешаешь неоднозначности (что живое, что мёртвое), ратифицируешь черновики, **глазами проверяешь git-базу** (см. главу про git — самый опасный момент именно здесь).
- **Агент:** Секция 1 — **обнаруживает реальную структуру** (НЕ предполагает `src/`), выводит фундамент по факту, не двигая код; Секция 2 — документирует живую коробку, **не передеплоивая**, нарушения блюпринта заносит в «Deviations / legacy risks»; аккуратно ставит git-базу.
- **Конец:** фундамент + `ai/` + (паспорт) + git-база. Проект стал «обычным гражданином» → дальше `/orient`, `/make-task`.

## 4. Выбор модели

Логика простая: **рассуждение — на сильной, дословное исполнение — на дешёвой.**

| Команда | Модель | Почему |
|---|---|---|
| `design-session`, `bootstrap`, `/make-task`, `/revise-task`, `/prune`, `/onboard` | **сильная** (Opus 4.8 / топ) | это проектирование и планирование — нужно рассуждение |
| `/run-task` | **дешёвая** (Kimi, Minimax, при желании Grok/Gemini) | план уже написан; задача — исполнить буквально |
| `/run-task` на сложной/комплексной задаче | **подними до Sonnet или Opus** | много файлов, тонкая логика — дешёвый споткнётся |
| `/orient` | **любая** | только чтение и сводка |

**Почему план пишется «под пол».** В момент планирования ты ещё не знаешь, какая модель его исполнит — может оказаться слабая. Поэтому план пишется под **самого слабого вероятного исполнителя**: всё прописано явно, ни один шаг не опирается на догадку. Сильная модель на переспецифицированном плане теряет почти ничего; слабая на недоспецифицированном — проваливается. **Переспецификация — безопасная ошибка.** И именно поэтому исполнитель следует плану дословно: авторитет — у явности и проверяемости плана, **а не у того, кто его написал**.

## 5. Паттерны и антипаттерны эксплуатации

**Что укрепляет контур:**

- **Стена планировщик↔исполнитель держится даже у соло-оператора.** Сидя за исполнителем (`/run-task`), ты следуешь плану дословно. Если план кривой — пишешь `blockers.md` и переключаешь шляпу на планировщика через `/revise-task`. Ты не правишь план, сидя в кресле исполнителя.
- **Авторитет — у плана, а не у автора.** Следуешь, потому что план явный и проверяемый. Где план расходится с кодом перед глазами — **побеждает реальность**: исполнитель пишет блокер, а не подгоняет одно под другое.
- **Дисциплина очереди.** Держи очередь мелкой. Две задачи, трогающие одни файлы, **не независимы** — либо явно последовательны в плане, либо слей их в одну.
- **Фундамент — первым делом и последним шагом, каждую задачу.** Это и есть «всегда-актуальный контекст».
- **Сохраняйся по ходу.** Точка сохранения на каждый законченный кусок реактивной работы. Эти коммиты — и запись работы, и то, по чему система считает отставание фундамента.

**Что ломает контур (узнай в лицо):**

- **«Поправлю сам как исполнитель, я ж помню замысел».** Самый сильный соблазн именно у соло-оператора, особенно когда исполнителем поднята сильная модель. Не поддавайся: кривой план — это `blockers.md` + `/revise-task`, **даже если план твой собственный**. Импровизация в кресле исполнителя — это как раз тот канал, по которому в систему втекают молчаливый дрейф и «призрачные» изменения без следа.
- **Копить несохранённое.** Работать час без единой точки сохранения, потому что «ещё не закончил». Сессия умирает вместе со всем, что в ней было.
- **Дать агенту «причесать» чужой код при онбординге.** Онбординг **документирует** реальность, он **не двигает, не переименовывает, не переписывает** код и не «дочиняет» коробку на живую. Любая реорганизация — отдельная осознанная работа потом.
- **Молчаливый дрейф фундамента.** Пропустить обновление фундамента в конце задачи или никогда не прунить. Устаревший фундамент — баг.
- **Слепой `git add .`** на папке с секретами и данными (см. главу про git).

## 6. Внедрение в существующий проект (`/onboard`)

Остальная семья предполагает «чистое поле»: решили → задокументировали → построили.
`/onboard` едет в обратную сторону — для того, что у тебя уже есть: код, написанный
до этой дисциплины, или коробка, развёрнутая до неё. Это **одноразовый** акт; после
него проект — обычный гражданин, и его дальше ведут `/make-task`, `/run-task`, `/prune`.

**Какие секции запускать** (тот же вопрос, что и в дизайн-сессии):

- есть **мой код** → Секция 1;
- есть **развёрнутая коробка** → Секция 2;
- и то, и другое → обе;
- чистый готовый сервис, развёрнутый давно (n8n, Postgres) → только Секция 2 (получит паспорт, без фундамента кода).

**Секция 1 — фундамент из существующего кода.** Агент **обнаруживает фактическую структуру, а не навязывает стандартную**. Он не ждёт `src/`: код может лежать плоско в корне, под одной или несколькими app-папками, вразброс. Агент инвентаризирует дерево, классифицирует (код / конфиг / данные / логи / доки / тесты / мусор) и ориентируется по тому, **что реально запускается** (entrypoints, манифесты зависимостей), а не по именам папок. Затем выводит лёгкий фундамент: `ARCHITECTURE.md` описывает layout **как он есть** (компоненты — концептуально, не пофайлово); `CONVENTIONS.md` фиксирует конвенции, которым код **уже следует**; `DECISIONS.md` стартует почти пустым с одной записью `## <дата> — onboarded` — историю прошлых решений агент **не выдумывает**.

**Что агент выносит тебе на разрешение** (код этого сам не покажет — решаешь ты):

- параллельные/дублирующиеся компоненты (две backend-папки) — что живое, что мёртвое;
- версионированные имена (`foo_v3_5.py` рядом со старыми) — что актуально;
- кладбища мёртвого кода (`trash/`, `old/`) — исключить из карты;
- чужие доки (`*.md`, `docs/`) — это **вход, не истина**; читаем, но что ещё верно — решаешь ты;
- уже существующую папку `ai/` — агент её **не затирает**, а осторожно сверяет.

**Секция 2 — паспорт из живой коробки.** Агент читает реальность только на чтение
(`docker-compose.yml`, `.env` с маскировкой, `sudo docker ps`, `sudo ss -tlnp`),
выводит `STACK.md` и **честно заносит нарушения старого деплоя** (сеть `bridge`, порт БД
на `0.0.0.0`, контейнер от root, нет compose-файла) в раздел «Deviations / legacy risks»
с пометкой «принято» или «надо исправить». **Он не чинит работающий стек.** Исправление —
это потом, по одному риску за раз, через `docker-deploy`, с его стоп-сигналами.

> **Главное про онбординг:** он **документирует и ратифицирует настоящее**, а не
> переделывает его. И именно здесь — самый опасный момент работы с git (следующая глава):
> папка уже набита `.env`, `data/`, `__pycache__` и бэкап-архивами, и слепой первый коммит
> утащит секреты и гигабайты в историю.

> **Пример.** Открыл старый проект: код плоско в корне, рядом папка `trash/` и каталог
> `backend_v2/` при живом `backend/`. Запускаешь `/onboard` на сильной модели. Агент строит
> карту, спрашивает: «`trash/` — выкинуть из карты? `backend_v2/` — это живое или брошенная
> попытка?». Ты отвечаешь, он документирует layout как есть, ставит `ai/` и git-базу, **ничего
> не переименовав**. Захочешь убрать `backend_v2/` — это уже отдельный `/make-task` потом.

## 7. Git с нуля

Это самая важная глава, и она написана, чтобы **снять страх**, а не добавить его.

### Что такое git — в одну фразу

> Для тебя git — это **кнопка «сохранить», кнопка «отменить» и машина времени для всего
> проекта сразу.** Не «система контроля версий», не «инструмент для команд». Кнопка, кнопка,
> машина времени.

### Чего в твоём контуре НЕ существует

Половина страха перед git — от слов, которых ты никогда не встретишь. В твоей работе
**нет и не будет**: веток, слияний (merge), rebase, cherry-pick, конфликтов, force-push,
`reset --hard`. Если где-то увидишь эти слова — это не про тебя. Ты работаешь в одну
прямую линию сохранений, и всё.

### Эмоциональный замок

> **Закоммиченное (сохранённое) потерять нельзя.** Пока ты пользуешься только набором
> команд ниже, вся работа git сводится к одному: гарантировать, что ты **всегда можешь
> вернуться к рабочему состоянию**. Сломать необратимо то, что уже сохранено, этими
> командами невозможно.

### Реальный режим: коммитит агент, не ты

В обычной жизни ты git почти не трогаешь. **Рутину коммитит агент сам** — в конце `/run-task`,
на каждом законченном куске реактивной работы, в конце `/prune` и `/onboard`. Каждая из этих команд заканчивается коммитом,
то есть очередной точкой сохранения. Твои руки нужны git только в двух случаях: один раз
настроить его на машине, и в редкий момент паники (аварийный набор ниже).

### Аварийный набор (выучи только эти пять)

```bash
git status          # где я и что изменилось с последнего сохранения. ВСЕГДА первая команда.
git log --oneline   # список точек сохранения, по строке на каждую, новые сверху.
git diff            # что именно поменялось в файлах (ещё не сохранённое).
git restore .       # выбросить НЕсохранённые изменения и вернуться к последнему сохранению.
git revert <hash>   # безопасно отменить УЖЕ сохранённое плохое (создаёт новый коммит).
```

Подробнее, простыми словами:

- **`git status`** — «где я нахожусь и что поменялось». С неё начинается любой разбор.
- **`git log --oneline`** — список твоих точек сохранения. `<hash>` — это короткий код слева
  в каждой строке; им ты адресуешь конкретную точку.
- **`git diff`** — показывает построчно, что изменилось с последнего сохранения, но ещё не
  сохранено. Полезно глянуть перед тем, как соглашаться на коммит.
- **`git restore .`** — «выкинуть весь несохранённый мусор и вернуть файлы к последнему
  сохранению». Это для «агент напортачил, я ещё не коммитил». *Тонкость:* если агент создал
  совсем новые файлы, git их пока не отслеживает — `restore` их не уберёт; такие просто
  удали вручную или попроси агента.
- **`git revert <hash>`** — «безопасно отменить уже сохранённое плохое». Создаёт **новый**
  коммит, который откатывает изменения указанного. Ничего не уничтожает, история цела —
  поэтому это безопасно. `<hash>` берёшь из `git log --oneline`.

> **Почему здесь НЕТ `reset --hard`.** Это единственная ходовая команда, которая умеет
> **необратимо** выбросить уже сохранённую работу и сделать твой эмоциональный замок
> неправдой. Тебе она не нужна ни разу: всё, что делает `reset --hard` «хорошего», безопасно
> делают `git restore` (для несохранённого) и `git revert` (для сохранённого). Если когда-нибудь
> почувствуешь, что «надо `reset --hard`» — это сигнал остановиться и позвать агента, а не жать.

### Настройка с нуля (один раз на машине)

```bash
git --version                                   # есть ли git вообще
# если нет, на Debian/Ubuntu:  sudo apt install git
git config --global user.name  "Твоё Имя"       # кто автор коммитов
git config --global user.email "you@example.com"
```

И в папке проекта (это обычно делает агент в `bootstrap`/`onboard`, но вот что под капотом):

```bash
cd /путь/к/проекту
git init               # завести машину времени в этой папке
# создать .gitignore (см. ниже) — ОБЯЗАТЕЛЬНО до первого add
git status             # посмотреть, что git собирается взять
git add .              # взять файлы под учёт — только ПОСЛЕ проверки .gitignore и status
git commit -m "initial"   # первая точка сохранения
```

`.gitignore` — список того, что git должен **игнорировать** (никогда не сохранять).
Минимум:

```gitignore
# секреты и данные — НИКОГДА в git
.env
.env.*
data/

# воспроизводимые зависимости (ставятся заново, в истории не нужны)
node_modules/
venv/
.venv/
__pycache__/

# бэкап-архивы
*.tar.gz
*.zip
*.bak
```

### Самый опасный момент: git-база при `/onboard`

Когда ты заводишь под git **старую** папку, она уже набита `.env`, `data/`, `__pycache__`
и бэкап-архивами. Слепой `git add .` утащит секреты и гигабайты в историю — а из истории
их потом вычищать больно. Поэтому ритм здесь **жёсткий и без исключений**:

```
1. сначала .gitignore   →   2. git status   →   3. глазами проверь, что в коммит
   НЕ попадают .env, data/, архивы   →   4. только теперь коммит
```

> **Никогда не делай `git add .` на онбординге, не посмотрев глазами `git status`.**
> Это единственный шаг во всей системе, где ошибка стоит дорого, и единственный, где агенту
> предписано остановиться и показать тебе список перед первым коммитом. Подтверждаешь — ты.

### Связь с системой

- **Provenance-штамп.** В плане задачи (`context.md`) поле «Based on» — это снимок, под
  который писался план. Им может быть git-ref (короткий `<hash>`), и тогда исполнитель
  автоматически ловит «план протух, пока ждал в очереди». **Есть и git-free вариант** —
  просто список файлов; система работает и без git, git лишь делает это чище.
- **Каждая рабочая команда заканчивается коммитом:** `/run-task`, `/prune`, `/onboard`,
  и каждый законченный кусок реактивной сессии. То есть после любой завершённой работы у тебя есть свежая точка возврата —
  без твоего участия.

### Мини-плейбук паники (git)

- **Агент напортачил, я ещё НЕ сохранял** (не было коммита после) → `git restore .`
- **Напортачил, и это УЖЕ сохранено** → `git log --oneline`, найди плохой коммит, `git revert <hash>`
- **Совсем потерялся** → `git status` (где я) → `git log --oneline` (куда вернуться) → найди
  последний хороший коммит → попроси агента безопасно вернуть к нему. Ничего не жми наугад.

## 8. Ритм обслуживания

Дрейф — это медленное расхождение документов с кодом: реактивные сессии поменяли поведение,
само-отчёты задач никто не перепроверял, `DECISIONS` распух, `ARCHITECTURE` описывает
то, чего уже нет. Лечится `/prune`. Когда запускать:

- **когда сторож сказал, что фундамент отстал**, ИЛИ
- **раз в 2–4 недели**, по календарю.

**Как считается дрейф.** Сторож берёт последний коммит, тронувший `ARCHITECTURE.md`, и считает,
сколько коммитов кода легло после него; порог — `foundation_lag_commits`. Счётчик сбрасывают
два якоря, побеждает ближний: сама карта сдвинулась, либо прошёл `/prune`. Считаются коммиты,
а не дни — сотня коммитов за две недели это дрейф, а один коммит через месяц — нет.

**Как замечать, не вспоминая.** Не держи это в голове — для этого есть `/orient`. Вернулся
в проект, запустил `/orient`, и в блоке «Foundation health» он сам скажет: *«N коммитов кода
с последнего обновления ARCHITECTURE.md — фундамент мог поплыть, запусти `/prune`»*, либо отметит замеченную
нестыковку (компонент в `ARCHITECTURE`, которого нет в коде; протухший план в очереди).
То есть рабочий цикл такой: **возвращаешься → `/orient` → он говорит, нужен ли `/prune`.**

## 9. Плейбук восстановления: «что-то сломалось»

Спокойно, по строкам. Найди свою ситуацию.

| Симптом | Что делать |
|---|---|
| Агент наизменял, я ещё **не коммитил** | `git restore .` — откат к последнему сохранению. |
| Агент наизменял, и это **уже закоммичено** | `git log --oneline` → найди плохой коммит → `git revert <hash>`. |
| **Совсем потерялся** в проекте | `git status`, потом `git log --oneline`, найди последний хороший коммит, позови агента вернуть к нему. |
| Не помню, **где остановился** | `/orient` — он прочтёт фундамент, очередь и историю и скажет следующий шаг. |
| Исполнитель остановился: **«план невыполним»** (`blockers.md`) | `/revise-task` (сильная модель) → потом `/run-task` снова. **Не** правь план руками в кресле исполнителя. |
| **Хотфикс перерос** потолок на полпути | пусть агент откатит начатое (`git restore .`, если не коммитил) → заводи `/make-task`. |
| Документы **разошлись с кодом** (`ARCHITECTURE` врёт) | `/prune` (сильная модель) — он предложит диффы, ты одобряешь. Противоречие код↔решение он вынесет тебе как развилку. |
| Открыл **старый проект/коробку** без фундамента | `/onboard` (сильная модель), один раз. Дальше — обычная петля. |
| Очередь **пуста**, не знаю, что делать | обсуди следующий шаг с агентом, согласуй план → `/make-task`. |

> Общий принцип паники: **сначала пойми, где ты** (`git status` / `/orient`), и только потом
> что-то нажимай. Почти всё откатывается `git restore` (несохранённое) или `git revert`
> (сохранённое). А кривой план — это всегда `blockers.md` + `/revise-task`, не импровизация.
