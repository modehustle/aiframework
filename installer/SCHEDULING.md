# Расписание: сторож, а не работник

> Проработка опыта «система напоминает о себе сама». Что здесь планировать по времени,
> что нельзя планировать в принципе, и как дать это из коробки, не завися от планировщика
> конкретного харнеса.

## Ловушка

Система действительно просится на крон, но **не в том месте, где кажется**. Два факта
из её собственного дизайна ломают наивный «раз в две недели гони `/prune`».

**Первое: метрика дрейфа — не календарь.** README задаёт триггер прунинга как
«после ~5 хотфиксов **ИЛИ** раз в 2–4 недели», и считает дрейф числом строк в
`ai/hotfix_log.md` после маркера `--- pruned <дата> ---`. Это счётчик **работы**, а не
времени. Проект, который никто не трогал три месяца, дрейфа не имеет — календарный крон
разбудит на нём `/prune`, потратит токены и не найдёт ничего. Проект, который долбили
неделю, набирает 8 хотфиксов и просит прунинга на четвёртый день, а календарь молчит
ещё десять.

**Второе, и это важнее: почти всё в системе требует ратификации человеком.** `/prune`
по конструкции «предлагает диффы — сам не переписывает», и каждый дифф ты одобряешь
руками; развилки «код прав или документ прав» он вообще обязан вынести тебе. `/run-task`
заканчивается вопросом «Принимаем результат?». Вся система стоит на том, что авторитет
у явного плана и у человека, а не у импровизации агента.

Значит **`/prune` по крону невозможно довести до конца в принципе** — он упрётся в
первое же «одобряешь?» и будет ждать. Не потому что мы плохо спроектировали расписание,
а потому что так задумана сама процедура.

## Что из этого следует

Планировать надо **обнаружение, а не действие**. По расписанию работает сторож, который
замечает и говорит; работу начинает человек.

Как только мы это приняли, задача резко упрощается, потому что **обнаружение не требует
модели**. Посмотри, что на самом деле надо проверить:

| Вопрос | Чем отвечается |
|---|---|
| Сколько хотфиксов с последнего прунинга? | число строк в `ai/hotfix_log.md` после маркера |
| Висит ли `blockers.md` и сколько дней? | наличие файла + mtime |
| Не протух ли план в очереди? | поле «Based on» в `context.md` против `git log` |
| Есть ли что исполнять? | непустой ли `ai/tasks/` |
| Не отстал ли фундамент от кода? | сколько коммитов кода легло с последнего обновления `ARCHITECTURE.md` (или с последнего `/prune`) |
| Не отстала ли версия самой системы? | штамп установки против центрального репозитория |

Ни одному из этих вопросов не нужен LLM. Это `git log`, mtime файлов и подсчёт строк —
то есть **обычный скрипт**: миллисекунды, ноль токенов, не нужен ключ API.

Вот и ответ на «это выходит за рамки просто воркфлоу». Выходит — но ровно на **один
маленький скрипт**, а не на платформу планирования. И скрипт этот везде одинаковый,
потому что читает файлы, которые наша же система и создала.

## Архитектура: три отделённых слоя

```
[1] СТОРОЖ      скрипт: читает файлы проекта → вердикт + exit code
                 универсален, наш, без модели и без сети
                          ↓
[2] ПЛАНИРОВЩИК  что есть в среде: hermes cron / Routines / OS cron / GitHub Actions
                 тонкий адаптер, взаимозаменяем
                          ↓
[3] ДЕЙСТВИЕ     человек запускает /prune, /revise-task, /run-task
                 уже написано, ничего не меняется
```

Разделение слоёв 1 и 2 — это то, что снимает исходную проблему «нет единого решения».
Нам **не нужно** единое решение: сторож возвращает exit code, а exit code умеет читать
любой планировщик на свете. Мы не выбираем один, мы поддерживаем любой.

И главное свойство: **сторож полезен вообще без планировщика.** Его первым делом зовёт
`/orient` — то есть ровно то, что README уже описывает как рабочий цикл («вернулся →
`/orient` → он говорит, нужен ли `/prune`»), только теперь вердикт детерминированный,
а не «агент посмотрел и прикинул». Расписание становится **необязательным апгрейдом**,
а не условием работы.

## Слой 1 — сторож

Один скрипт, который в проекте отвечает на вопросы из таблицы выше.

**Контракт:**

- `--json` — машинный вердикт (для флотского обхода и для агента);
- человекочитаемый вывод по умолчанию;
- **exit code:** `0` — здоров, `1` — есть что показать человеку, `2` — сломан контур
  (нет `ai/`, нет фундамента — проект не под системой);
- **ничего не пишет.** Сторож — read-only, как `/orient`.

**Кто его зовёт:**

- `/orient` — при каждом возвращении в проект (это уже описанное поведение, просто
  становится точным);
- планировщик — если настроен;
- человек руками, когда захочет.

Скрипт кладётся рядом с процедурами при установке. Он не ломает наше правило «процедура —
один файл»: правило про `SKILL.md`, а это отдельный исполняемый артефакт инсталлера.

## Слой 2 — планировщики

Тот же приём, что и с инсталлером: одно каноническое определение задания, тонкие адаптеры.

| Среда | Механизм | Комментарий |
|---|---|---|
| **Hermes** | `hermes cron create` + `hermes cron start` | Лучший в списке. Демон, `cron list/status`, пиннинг модели и `--reasoning-effort` на конкретную джобу, вывод в `~/.hermes/cron/output/`, доставка в подключённую платформу. **Валидирует конфиг до LLM-вызова**: при провале ставит `blocked_config`, шлёт один алерт и не тратит модель — ровно та дисциплина, которую нам стоит скопировать. |
| **Claude Code** | Cloud Routines (крон + вебхук, инфраструктура Anthropic, с апреля 2026); Desktop Scheduled Tasks; `/loop` в пределах сессии | Routines не требуют своего сервера — машину можно выключать. |
| **Любой харнес с headless-режимом** | OS cron / systemd timer / launchd + `claude -p`, `codex exec`, аналоги | Универсальный запасной вариант. `codex exec` по умолчанию в read-only песочнице, отдаёт осмысленный exit code и `--json` — для сторожа идеально. |
| **Проект в git** | GitHub Actions, `on: schedule` | Единственный вариант, **вообще не зависящий от харнеса**. И он доступен всегда: наша система требует git по конструкции (provenance-штампы, коммит в конце каждой команды), так что репозиторий есть у каждого проекта. |

Адаптер в каждом случае — это несколько строк, генерирующих запись расписания, которая
зовёт сторожа. Логика живёт в стороже, планировщик её только будит.

## Слой 3 — флотский обход

Здесь настоящая ценность, ради которой всё и затевается.

Крон **на один проект** даёт мало: ты и так в нём сидишь, и `/orient` при входе всё
скажет. Чего соло-оператор физически не может — это помнить, который из его двенадцати
проектов поплыл. Вот это и надо автоматизировать.

Одно задание в расписании → обходит реестр проектов → гоняет сторожа на каждом →
отдаёт **одну** сводку:

```
fraim · 3 из 12 проектов просят внимания

  payments-api   7 хотфиксов с последнего прунинга          → /prune
  crm-sync       blockers.md висит 9 дней                   → /revise-task
  scraper        план протух: Based on d96282e, HEAD ушёл на 4 коммита
```

Обход детерминированный, поэтому гонять его можно хоть ежечасно — он не стоит ничего.
Модель включается только если ты пошёл по строке из сводки.

**Реестр** — простой список путей, `~/.fraim/projects`. Ведёт его инсталлер, а
пополняют его `bootstrap` и `onboard`: обе процедуры и так завершаются постановкой
проекта под систему, регистрация — одна строка в конец каждой. Отдельной ручной работы
это не создаёт.

## Чего не делать

Три ошибки, каждая из которых убивает пользу.

**Не планировать мутирующие действия.** Ни `/prune`, ни `/run-task`, ни `/hotfix` не
запускаются по расписанию без человека. Это не осторожность, это следствие дизайна:
обе процедуры по конструкции останавливаются и спрашивают. Сторож замечает — человек
решает. Автономная правка кода по будильнику — это ровно тот «молчаливый дрейф», против
которого построена вся система.

**Не совать модель в проверку.** Ночной LLM-обход двенадцати проектов — это реальные
деньги за ответ «всё в порядке» в девяти случаях из десяти. Проверка обязана быть
детерминированной; модель — только в действии.

**Не слать «всё хорошо».** Сводка, которая каждое утро рапортует, что всё в порядке,
перестаёт читаться за неделю — и в тот единственный день, когда в ней будет что-то
важное, её тоже не прочитают. Правило: **молчание = здоров**, сообщение приходит только
при непустом результате.

## Что это добавляет к системе

Изменения минимальные и ложатся в существующие места:

1. **Новый артефакт** — скрипт-сторож в `installer/`. Первое в продукте, что не markdown.
2. **`orient`** — вместо «агент посмотрит и прикинет» зовёт сторожа и докладывает его
   вердикт. Блок «Foundation health» уже существует, меняется только источник данных.
3. **`bootstrap` и `onboard`** — по строке в конце: зарегистрировать проект в реестре.
4. **Реестр** `~/.fraim/projects` — ведёт инсталлер.

Ни одна процедура не переписывается, новых команд для человека не появляется.

## Открытые вопросы

- **Куда доставлять сводку.** Hermes умеет отдавать результат в подключённую платформу,
  Claude Code Routines — свои каналы, OS cron — в лучшем случае в файл или почту. Нужен ли
  нам один канал доставки поверх всех (тогда какой), или сводка просто ложится файлом,
  а доставку каждый настраивает сам? Это единственное решение здесь, которое я бы не
  принимал за тебя.
- ~~**Язык сторожа.**~~ **Решено: POSIX shell.** Нулевые зависимости здесь не удобство,
  а требование — сторож обязан запускаться в контейнере, в Actions и на голом сервере.
  Рантайм понадобился бы ровно там, где сторожу он не нужен.
- **Порог тишины.** «5 хотфиксов» README задаёт как ориентир, а не как закон. Стоит ли
  делать порог настраиваемым на проект (например, в `ai/`), или единый порог честнее.
