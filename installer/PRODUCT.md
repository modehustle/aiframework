## Сквозной принцип

Сессия начиналась с вопроса «в каком формате раскладывать файлы под каждый агент»,
а закончилась другим ответом. Настоящая линия раздела в продукте — не между
форматами, а между **состоянием и текстом**:

| | Текст | Состояние |
|---|---|---|
| Что это | процедуры, инструкции, планы | что где установлено, какие проекты есть, сколько дрейфа накопилось |
| Свойства | переносим, версионируем, работает без рантайма | привязано к машине, меняется само, требует исполнения |
| Форма | markdown | исполняемый код |

Каждое решение ниже — частный случай этого разделения. Установка системы (состояние)
отделена от разворота в проекте (текст). Сторож (состояние) отделён от процедуры
(текст). CLI (состояние) отделён от скиллов (текст). Если в будущем возникнет спор,
куда положить новую функцию, — вопрос всегда один: это состояние или текст.

## Позиционирование

### Мы не первые, и это хорошая новость

К августу 2026 **spec-driven development** — сложившаяся категория. AWS выпустил
**Kiro** (международный запуск 7 мая 2026), где SDD зашит в IDE как основной режим
работы. У GitHub есть **Spec Kit** — Python-CLI, 93 000+ звёзд, поддержка 30+ агентов.
Есть BMAD-METHOD и с десяток инструментов помельче.

Канонический воркфлоу категории — **Requirements → Design → Tasks, код последним**.
Это наши `design-session → make-task → run-task`. Категория возникла как прямой ответ
на провал вайб-кодинга: агенты выдают правдоподобный код, который дрейфует от замысла
и разлагается с ростом проекта.

Вывод: система не странная надстройка. Она независимо пришла туда же, куда пришли
Amazon, GitHub и остальные. Совпадение диагноза и структуры лечения — это подтверждение,
а не повод для тревоги.

### Чего нет ни у кого

Три вещи отличают систему от всей категории:

**1. Учёт дрейфа.** Хотфикс-лог как счётчик, маркер прунинга, порог срабатывания по
числу правок, а не по календарю. Индустрия признаёт эту проблему нерешённой прямым
текстом: «ручные `AGENTS.md` упираются в фундаментальную проблему сопровождения —
контекстные файлы дрейфуют по мере развития кодовой базы, и **автоматического способа
обнаружить устаревание не существует**». У нас он есть.

**2. Стена между планировщиком и исполнителем.** Исполнитель не имеет права чинить
план: он пишет `blockers.md` и останавливается. Это контрарно — рынок движется в
сторону *большей* автономии агента, — и это осознанная ставка против тренда.

**3. Вторая половина жизненного цикла.** SDD-инструменты покрывают рождение проекта:
спека → код. У нас есть `onboard` для доставшегося legacy, реактивный режим как основной,
`prune` для обслуживания, `orient` для возврата после паузы. **Эксплуатацию не покрывает
никто.** Все продают, как проект начать; никто — как его вести полгода спустя.

### Позиция одной фразой

> Не «ещё один SDD-инструмент», а **эксплуатационный слой**: то, что происходит с
> проектом после того, как первая спека исполнена.

Целевой пользователь — соло-оператор, ведущий несколько проектов на агентах и
возвращающийся в каждый после пауз. Именно у него дрейф и потеря контекста между
чатами болят сильнее всего, а помощи от команды нет.

### Честный риск

Не «это никому не нужно», а **соотношение церемонии и пользы в чужом контексте**.
Соло-оператор с дюжиной проектов — дисциплина окупается. Команда на одной кодовой
базе с сильной моделью — часть ритуала будет ощущаться налогом.

Отдельно: аргумент «пиши план под пол, исполняй на дешёвой модели» держался на большом
разрыве между тирами. Разрыв сужается. Но ни одна из трёх оригинальных вещей выше на
тир модели не завязана — просядет экономический аргумент, а не система.

## Архитектура продукта

Три компонента, граница между ними — по сквозному принципу.

| Компонент | Владеет | Форма | Почему именно так |
|---|---|---|---|
| **CLI** | установка, обновление, реестр проектов, сторож, флотский обход, настройка расписания | исполняемый файл на машине | это состояние и жизненный цикл — markdown так не умеет в принципе |
| **Процедурные скиллы** | 13 текстов процедур | `SKILL.md` на диске | 13–23 КБ каждый; нужны там, где CLI может не быть (контейнер, CI, веб-сессия); автотриггерятся по описанию |
| **Мастер-скилл** | пульт: статус, сводка по флоту, следующий шаг | один `SKILL.md` | единственный способ дать агенту доступ к **межпроектному** состоянию |

Ключевое: **CLI не отдаёт тексты процедур.** Он их устанавливает, но во время работы
агент читает файлы с диска, а не получает их через stdout. Две причины — размер
(23 КБ через вывод баш-команды часть харнесов обрежет) и среда (в CI или веб-сессии
CLI может не стоять, а файл скилла лежит).

## CLI

### Установка

```bash
curl -fsSL https://raw.githubusercontent.com/modehustle/aiframework/main/installer/install.sh | sh
fraim init               # находит харнесы, ставит скиллы, заводит реестр
```

Одна команда в терминале — это и есть требование к продукту. Всё остальное `init`
делает сам.

**`init` идемпотентен.** Та же команда — это установка, обновление и подключение
только что появившегося харнеса. Отдельного `update` учить не нужно (он остаётся
как явный синоним).

Что `init` делает конкретно:

1. определяет установленные харнесы (см. [HARNESS_TARGETS.md](HARNESS_TARGETS.md));
2. генерирует из `procedures/` каталоги формата Agent Skills и раскладывает по целевым
   путям каждого найденного харнеса;
3. ставит мастер-скилл;
4. дописывает блок в `AGENTS.md` (контекстный слой);
5. регистрирует текущий проект в реестре, если он под системой;
6. прописывает разрешение на запуск `fraim` там, где харнес гейтит shell —
   иначе пульт будет упираться в запрос доступа на каждый чих.

### Подкоманды

| Команда | Что делает |
|---|---|
| `init` | установка / обновление / подключение нового харнеса |
| `status` | сторож по текущему проекту: дрейф, очередь, блокеры, свежесть фундамента |
| `sweep` | флотский обход: одна сводка по всем проектам реестра |
| `projects` | показать / добавить / убрать проекты в реестре |
| `schedule` | настроить регулярный `sweep` через планировщик, который есть в среде |
| `doctor` | что и куда установлено, какая версия, что разошлось |
| `show <имя>` | напечатать текст процедуры (для отладки и для сред без скиллов) |

`status` и `sweep` — детерминированные, без модели: чтение файлов, `git log` и mtime.
Поэтому их не жалко звать хоть ежечасно. Подробнее — [SCHEDULING.md](SCHEDULING.md).

### Расписание настраивает CLI, а не агент

`schedule` меняет crontab, systemd timer или конфиг планировщика харнеса — то есть
трогает **хост**. Здесь мы следуем прецеденту, который в системе уже есть: в
`docker-deploy` хостовые действия агент не выполняет, он останавливается и просит
человека. То же правило: механизмом владеет CLI, запускает его человек, агент может
предложить и показать команду, но не выполняет молча.

## Мастер-скилл

Один `SKILL.md`, тонкий — таблица маршрутизации, а не пересказ системы.

Содержит: что это за система в трёх строках, таблицу подкоманд CLI, как читать сводку,
и указание, что сами процедуры вызываются своими скиллами (`/make-task`, `/run-task`…).

**Зачем он нужен отдельно от процедурных.** У них разная поверхность
срабатывания. Процедурные скиллы триггерятся на задачу («давай сделаем фичу» →
`make-task`). Мастер-скилл триггерится на **вопрос об ориентации**: «где я остановился»,
«что требует внимания», «какие проекты поплыли». Это ровно тот момент возвращения
в работу, вокруг которого построен `orient`, — и единственный момент, когда агенту
нужно знать про другие проекты, а не про текущий.

## Отвергнутые альтернативы

| Отвергнуто | Почему |
|---|---|
| Свой формат под каждый харнес как основной путь | Agent Skills — открытый стандарт, покрывает 6 из 12 харнесов и ~69% токенов топ-10. Изобретать нечего, надо попасть в существующее. |
| MCP как основная доставка | Красиво решает синк (процедуры отдаются в момент вызова), но вызов идёт через tool, а не через `/команду`, и тянет хостинг. Оставлено на «потом». |
| `~/.codex/prompts/` у Codex | Формат почти совпадает с Claude Code, но официально задепрекейчен в пользу skills и вдобавок сломан в 0.117.0. |
| `kilo.jsonc` сейчас | v7 — движущаяся мишень, старые rules уже выпилены. Берём `~/.kilocode/workflows/` как дешёвый и обратимый вариант. |
| `/prune` по крону | Процедура по конструкции предлагает диффы и ждёт одобрения на каждый. Довести до конца без человека нельзя — не из осторожности, а по дизайну. |
| Модель внутри периодической проверки | Ночной LLM-обход двенадцати проектов — деньги за ответ «всё в порядке» в девяти случаях из десяти. Проверка детерминированная, модель только в действии. |
| Мастер-скилл **вместо** процедурных | Процедуры весят 13–23 КБ: через stdout часть харнесов обрежет. Плюс скилл работает без рантайма, а CLI в CI или веб-сессии может не быть. |
| Ежедневная сводка «всё хорошо» | Перестаёт читаться за неделю, и важное сообщение тонет вместе с ней. Молчание = здоров. |
| Имена команд через подчёркивание (`/make_task`) | Стандарт Agent Skills требует kebab-case (`^[a-z0-9-]+$`). Раз мы целимся в стандарт, а не изобретаем формат, имена переехали на `/make-task`, `/run-task`, `/revise-task`, `/reconcile-task`, `/design-session`, `/docker-deploy`. |
| Одна процедура на сборку коробки и на впуск трафика | Сборка безопасного контейнера одинакова везде, впуск трафика — нет. В одном файле вариативность среды протекала на весь документ и делала «universal» рассказом про один сервер. Разрезано на `/docker-deploy` и `/expose`. |
| Дефолтный реверс-прокси в `/expose` | Дефолт — это чья-то среда, вписанная как норма (принцип C1). Правильный ответ — тот edge, который на хосте уже стоит; когда нет ничего, выбор делает человек из меню рецептов. |
| Раскладку проекта воспроизводит модель по прозе | Детерминированную работу поручали недетерминированному исполнителю. Форма — код (`fraim scaffold`), наполнение — текст (`/bootstrap`, `/onboard`). |
| Пустые файлы фундамента при разворачивании | Пустой `ARCHITECTURE.md` хуже отсутствующего: и сторож, и агент считают его признаком здоровья. Решение — маркер `fraim:stub` и третье состояние у сторожа. |
| Прозаический запасной путь, когда CLI не установлен | Две реализации одного детерминированного действия неизбежно разойдутся. Нет `fraim` — процедура останавливается, как `/docker-deploy` на хостовых действиях. |
| Хуки харнеса как основной способ принуждения | У каждого харнеса свои события, у части их нет. Гейт (`task-seal`) не нуждается в событии: единственный выход из задачи принадлежит нам, и это работает везде, где есть shell. |
| Флаг `--force` у гейта | Гейт, который обходится флагом, — не гейт. Отход есть, но он записан: исполнитель вправе не тронуть фундамент, но обязан сказать об этом в `result.md`. |
| Рукописный `manifest.json` как источник правды | Раздвоил бы источник: описание жило бы и в манифесте, и во фронтматтере скилла, и они бы разошлись. Источник — фронтматтер процедуры, манифест генерируется из него. |

## Открытые вопросы

- **Куда доставлять сводку `sweep`.** Hermes умеет отдавать результат в подключённую
  платформу, у Claude Code Routines свои каналы, у OS cron — файл или почта. Нужен ли
  общий канал поверх всех (тогда какой), или сводка ложится файлом, а доставку каждый
  настраивает сам. Заметно влияет на объём v1.
- ~~**Язык CLI.**~~ **Решено: POSIX shell целиком.** Тот же довод, что и у сторожа
  ([SCHEDULING.md](SCHEDULING.md)), плюс: поверхность CLI мала и по природе файловая —
  копирование каталогов, `git log`, mtime. Node сделал бы `npm i -g` естественнее, но
  раздвоил бы продукт на два языка ради одной команды установки. npm-обёртку можно
  добавить сверху, когда понадобится.
- ~~**Имя и короткий алиас.**~~ **Решено: `fraim`.** Репозиторий остаётся `aiframework`,
  команда, каталог состояния (`~/.fraim/`) и скилл-пульт называются `fraim`.
- ~~**Порог тишины сторожа.**~~ **Решено: настраивается на проект.** `hotfix_threshold`
  в `ai/fraim.conf`, вместе с порогом отставания фундамента, порогом протухания плана и
  выключателями отдельных проверок. Едет в git вместе с репозиторием.
