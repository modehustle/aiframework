## Главный вывод

Три вещи, и вторая важнее первой.

**1. Класс существует и он огромен.** Публичный каталог оркестраторов агентов на сентябрь
2026 содержит более сотни живых проектов, разбитых на шесть подклассов. «Параллельные
агенты в воркtree с пультом» — это два из шести подклассов, и в них десятки инструментов.
Гипотеза владельца «это тренд» подтверждается: спорить не с чем.

**2. Именно поэтому таблица адаптеров «под каждую ADE» — беговая дорожка.** Это ровно тот
случай, о котором [P0](../PRINCIPLES.md#p0-продукт-для-того-кто-не-профессиональный-разработчик)
говорит прямым текстом: широта — беговая дорожка, вариантов всегда больше, чем сил. Поддержка
класса невозможна; возможна поддержка **контракта**. И контракт отсеивает жёстко: подавляющее
большинство инструментов класса — десктоп или TUI, у них нет CLI вообще, а значит дирижёр
физически не может ими управлять.

**3. Ниша, в которую мы целимся, уже не пуста.** В том же каталоге есть подкласс
«инфраструктура и примитивы», где несколько проектов делают ровно то, что мы собирались
делать `dispatch-check`'ом и гейтом сборки: объявление намерения до записи кода,
детерминированное обнаружение столкновений планов, приёмка через проверочный прогон. Это не
повод отступать, но повод переформулировать отличие точнее, чем «мы дирижируем ADE».
Разбор — [ниже](#неприятная-находка-соседи-по-нише).

## Метод и чего он не даёт

**Что сделано:** поиск по классу, полное чтение публичного каталога оркестраторов,
полное чтение обоих skill-guide'ов Orca (`orca-cli`, `orchestration` — 28 и 44 КБ), точечные
проверки по отдельным кандидатам.

**Чего этот проход не даёт, и это надо знать при чтении:**

- **Нет ранжирования по популярности.** У [HARNESS_TARGETS.md](HARNESS_TARGETS.md) была
  честная ось — расход токенов по рейтингу OpenRouter. Здесь такой оси нет: сопоставимого
  публичного рейтинга по этому классу не нашлось, а собрать звёзды по сотне репозиториев в
  этой сессии нельзя — доступ к GitHub API ограничен одним репозиторием. Поэтому таблицы
  «топ-10» здесь нет и порядок в списках **ничего не означает**.
- **Почти всё — со слов каталога.** Описания инструментов ниже принадлежат его автору, а не
  проверены мной. Единственное исключение — Orca: её возможности прочитаны в её собственной
  документации.
- **Официальная документация Orca недоступна из этой среды**: `onorca.dev` блокируется
  сетевой политикой. Всё, что известно про `orca serve`, собрано из репозитория проекта и
  выдачи поиска.

Помечено везде: **[док]** — прочитано в первоисточнике, **[кат]** — со слов каталога,
**[поиск]** — из выдачи поиска.

## Класс оказался не одним классом

Каталог делит поле на шесть подклассов. Для нас они не равнозначны — три из шести к дирижёру
отношения не имеют вовсе:

| Подкласс | Что это | Наш интерес |
|---|---|---|
| **Параллельные агенты — терминал (TUI/CLI)** | tmux, воркtree, TUI-дашборд | **да**, если есть скриптуемая поверхность |
| **Параллельные агенты — десктоп и веб** | то же в GUI, с ревью диффов и слиянием | **да**, у кого есть CLI/API |
| **Мультиагентные рои** | агенты сами делят работу и общаются | нет: они хотят быть дирижёром, а не средой |
| **Автономные loop-runner'ы** | один агент в цикле «пока не сойдётся» | нет: это режим, а не среда |
| **Автономные task-runner'ы** | работа приезжает из трекера, борда или расписания | нет, но см. §7 [MODES.md](../MODES.md#7-расписание-глаголов-уточнение-d4) |
| **Инфраструктура и примитивы** | control plane, протоколы координации, адаптеры | **осторожно**: тут наши соседи |

Вывод, который стоит записать: **«ADE» — не синоним «оркестратора».** Нам нужна среда,
которая даёт изоляцию и запускает named-агента по команде. Инструмент, который сам решает,
что кому делать, — не среда, а конкурирующий дирижёр, и интегрироваться с ним нельзя, можно
только выбрать одного из двух.

## Отсев: у кого есть поверхность для агента

Единственный вопрос первого прохода: **может ли этим управлять агент, а не человек мышкой.**
Инструменты, у которых в описании заявлена CLI, API или сокет:

| Инструмент | Заявленная поверхность | Источник |
|---|---|---|
| **Orca** | полноценный CLI, `--json` у каждой команды, стабильные коды ошибок, оркестрационный слой поверх; `orca serve` — headless-рантайм, к которому цепляются десктоп и телефон | **[док]** |
| **Emdash** | headless CLI (`list / create / remove / send`) над той же SQLite и теми же воркtree, что и десктоп; флаги `--project --branch --base --name --prompt --agent --json`; `.emdash.json` со сценариями setup/run/teardown на задачу | **[поиск]** |
| **bb** | десктоп, веб, CLI и HTTP API | **[кат]** |
| **herdr** | фоновой рантайм, сессии переживают перезагрузку, агенты сами открывают панели через CLI и сокет | **[кат]** |
| **Paseo** | самохостируемый демон, управление с десктопа, телефона, веба и CLI | **[кат]** |
| **agterm** | скриптуемый control API | **[кат]** |
| **Ouijit** | session-aware CLI, хуки жизненного цикла, воркtree на задачу | **[кат]** |
| **vibe-tree** | десктоп, веб и CLI | **[кат]** |
| **Open Session** | самохостируемый сервер, воркtree, веб-UI, интеграции | **[кат]** |
| **sandbox-agent** | демон, HTTP/SSE API и SDK для шести агентов в пяти песочницах | **[кат]** |

Всё остальное в подклассах «параллельные агенты» — десктоп или TUI без заявленного
программного интерфейса. Для дирижёра они не существуют: не потому, что плохи, а потому что
их поверхность — человек.

> Отдельно стоит заметить **Emdash**: у него есть штука, которой нет у остальных и которая
> нам важна не как фича, а как признак зрелости, — `$EMDASH_PORT` на задачу, то есть решённая
> проблема «пять воркtree дерутся за один порт разработки». Это та деталь, которую находят
> только те, кто реально гонял флот. **[поиск]**

## Контракт из шести операций: кто отвечает

Контракт — [MODES.md §9](../MODES.md#9-контракт-ade--шесть-операций). Напоминание, зачем он:
без операции №5 (сигнал завершения с исходом) дирижёр вынужден читать вывод терминала и
догадываться, чем нарушает собственный инвариант — сверяться с деревом, а не с прозой.

| Операция | Orca | Emdash | Остальные |
|---|---|---|---|
| 1. изолированный чекаут по имени и базе | `worktree create --name --base-branch` **[док]** | `create --branch --base` **[поиск]** | не проверено |
| 2. named-агент с моделью | `--agent claude\|codex\|omp\|pi\|grok`, `worker-start --model --effort` **[док]** | `--agent` **[поиск]** | не проверено |
| 3. передать задание | `--prompt`, `terminal send`, `dispatch --inject` **[док]** | `send` **[поиск]** | не проверено |
| 4. жив или закончил | `terminal wait --for tui-idle`, `worker-show` **[док]** | не найдено | не проверено |
| 5. **исход завершения** | `worker_done --outcome succeeded\|failed` **[док]** | **не найдено** | не проверено |
| 6. убрать за собой | `worker-release` — закрывает ровно свой терминал, чужие удерживает **[док]** | `remove` **[поиск]** | не проверено |

**Читается это так.** Контракту заведомо отвечает **одна** среда — Orca, и отвечает с
запасом: у неё есть не только шесть операций, но и целый слой поверх них (DAG задач,
инбоксы, блокирующий ask/reply, circuit breaker после трёх неудач, разделение
supervised/unsupervised). Emdash — сильный второй кандидат по первым трём операциям, но
именно по решающей пятой у меня нет данных, и это первое, что должен проверить второй проход.

Практический вывод для проектирования: **строим под контракт, реализуем на Orca, вторую
строку в таблице не пишем, пока не появится кандидат, у которого проверена операция №5.**
Одна проверенная реализация лучше двух предположительных — это [B2](../PRINCIPLES.md#b2-у-детерминированного-действия-ровно-одна-реализация)
в чистом виде.

## Неприятная находка: соседи по нише

Мы собирались отличаться тем, что «поверх флота держим дисциплину: проверяем пересечение
планов до раздачи и не даём принять результат без человека». В подклассе «инфраструктура и
примитивы» это делают уже несколько проектов. Все описания — **[кат]**:

- **foremerge** — «протокол координации поверх Git: агенты объявляют намерение, семантическую
  область и операцию **до** того, как писать код; детерминированные правила выдают находки,
  когда планы сталкиваются; приёмка гейтится проверочным прогоном, который он выполняет сам».
  Это буквально `dispatch-check` плюс гейт сборки, одним бинарником на Rust поверх SQLite.
- **Concord MCP** — «общий протокол координации: агенты забирают работу, обнаруживают
  столкновения правок, обмениваются устойчивыми сообщениями, передают владение и сдают
  доказательства ревью, **не заменяя существующие харнесы**». Позиционирование слово в слово
  наше.
- **wit** — блокирует не файлы, а отдельные функции через Tree-sitter и предупреждает агента
  о конфликте до записи. Точнее нашего по гранулярности. *(в каталоге помечен как спящий —
  нет коммитов несколько месяцев)*
- **gnap** — «git-native протокол: агенты координируются через общий репозиторий как доску
  задач, без процесса-оркестратора». Наша же идея «правда живёт в git». *(тоже спящий)*
- **NEEDLE** — очередь задач в SQLite с атомарными захватами, каждая задача уходит в headless
  CLI, каждый исход проходит через явный конечный автомат; межагентного канала нет,
  координация делается **на этапе декомпозиции**. Это близко к нашему «пересечение проверяем
  до раздачи».
- **Archon** — «конструктор харнесов для детерминированных рабочих процессов: шаги агента
  плюс скрипты, проверочные гейты, одобрения и изолированные воркtree».
- **ivy-tendril** — «ведёт агентов по жизненному циклу на основе плана, с проверочными
  гейтами, самообучающейся памятью и человеческими чекпойнтами».

**Что это означает честно.** Идея «дисциплина поверх флота» не наша собственная, она носится
в воздухе, и несколько команд пришли к ней независимо. Наше отличие придётся формулировать
не через механику (её повторили), а через то, чего у них нет:

1. **У них нет плана как артефакта.** У foremerge агенты *объявляют* намерение — это заявка
   агента в момент старта. У нас `Files to Change` — это поле **запечатанного плана**,
   написанного планировщиком, лежащего в git и проверяемого гейтом. Разница та же, что между
   «агент сказал, что собирается» и «человек ратифицировал, что будет сделано».
2. **У них нет второй половины жизненного цикла.** Дрейф, фундамент, прунинг, возвращение в
   проект после паузы — то, что [PRODUCT.md](PRODUCT.md) называет нашим третьим отличием.
   Координация столкновений — это про момент работы; наш продукт про то, что происходит
   между моментами работы.
3. **У них другая аудитория.** Это инструменты для тех, кто держит флот из 20 агентов.
   Наш пользователь — соло-оператор с дюжиной проектов и без экспертизы в git
   ([P0](../PRINCIPLES.md#p0-продукт-для-того-кто-не-профессиональный-разработчик)).

И один вывод, который стоит принять сразу: **`dispatch-check` — не продукт, а функция внутри
продукта, который уже владеет планами.** Как отдельная ценность он проигрывает foremerge и не
надо делать вид, что нет. Как гейт над нашим планом он делает то, чего foremerge сделать не
может, — потому что у него нет нашего плана.

## Стандарты: почему C3 здесь не срабатывает

[C3](../PRINCIPLES.md#c3-целиться-в-существующий-стандарт-а-не-изобретать-формат) велит целиться
в существующий стандарт. На первой оси это сработало блестяще: Agent Skills существовали, и мы
в них попали. Здесь — не срабатывает, и это надо зафиксировать, чтобы не искать заново.

Три протокола, которые есть на сентябрь 2026 **[поиск]**:

| Протокол | Что связывает | Наш ли шов |
|---|---|---|
| **MCP** | агента с инструментами | нет |
| **ACP** (Agent Client Protocol) | **редактор с агентом**; JSON-RPC, введён Zed в августе 2025, подхвачен JetBrains, реестр с января 2026 | нет: он про IDE↔агент, а не про «дай изолированный чекаут и запусти в нём named-агента» |
| **A2A** | агента с агентом | нет: это про переговоры равных, а у нас дирижёр и воркер |

**Стандарта для нашего шва не существует.** Контракт из шести операций — не переизобретение
чужого формата, а описание дыры. Это меняет тон вывода: мы не нарушаем C3, мы попали в место,
где стандарта пока нет.

Держать в поле зрения стоит **ACP**: он ближе всех и уже расползается за пределы редакторов
(OpenHands, по описанию каталога, водит «Claude Code, Codex и любого ACP-агента»). Если ACP
или его наследник дорастёт до операций 1 и 5, правильным ходом станет попасть в него, а свою
таблицу выбросить.

## Рекомендация

1. **Целимся в контракт, реализуем на Orca.** Единственная среда, у которой проверены все
   шесть операций. Вторую строку в таблице адаптеров не заводить, пока у кандидата не
   проверена операция №5 руками.
2. **Таблицу адаптеров всё равно строим** — той же формы, что `harness_table()`: строка на
   среду, логика общая. Не ради второй строки завтра, а чтобы Orca-специфика не растеклась по
   коду; тогда вторая строка будет стоить час, а не переписывание.
3. **Emdash — первый кандидат на проверку** во втором проходе: единственный, у кого CLI
   заявлен как полноценный и headless, а не как «есть немного».
4. **Отличие переформулировать** по трём пунктам из раздела о соседях, и сделать это до кода,
   а не после. Если после проверки окажется, что foremerge или Concord закрывают нашу
   ценность целиком — честнее интегрироваться с ними, чем повторять.
5. **ACP — на наблюдение**, с пересмотром через полгода.

## Что должен померить второй проход

Первый проход отвечал «кто вообще есть». Второй отвечает «кто годится», и это работа руками,
а не поиском.

**По каждому кандидату из отсева:**

- операция №5 — есть ли машинно читаемый **исход** завершения, или его надо угадывать по
  выводу терминала (это отсекающий вопрос);
- операция №6 — что именно убирает уборка: только своё или всё в рабочем пространстве
  ([B6](../PRINCIPLES.md#b6-глагол-трогает-только-то-что-сам-изменил));
- поведение при перезапуске среды: переживают ли ручки/идентификаторы падение рантайма
  (от этого зависит, что мы обязаны хранить у себя в git, а что можно держать кэшем);
- бинарь на PATH и его имя — с проверкой на конфликты (у Orca на Linux голый `orca` — это
  программа чтения с экрана GNOME, и её запуск включает синтез речи; CLI там `orca-ide`);
- лицензия и способ распространения.

**По классу в целом:**

- есть ли публичная ось популярности, появившаяся с сентября 2026, — без неё приоритет строк
  в таблице придётся ставить по своему опыту, и это надо признать вслух;
- живы ли соседи по нише (foremerge, Concord MCP) и сдвинулись ли они в сторону нашей
  аудитории.

**Практическая проверка, которая стоит десяти поисков:** поставить Orca и Emdash на одну
машину и прогнать через каждую один и тот же сценарий — «создать чекаут, запустить codex с
промптом, дождаться исхода, убрать за собой». Всё, что важно, выяснится в первые полчаса.
